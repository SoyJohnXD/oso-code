### Parallel — the wave loop

Everything above is the SEQUENTIAL path: one slice at a time in the main checkout, where "never two at once" is the rule. PARALLEL changes what that rule counts. The unit is the WAVE (§4), a set of slices with no edge between any two of them. Each slice runs the four steps above inside its OWN worktree, and one wave goes from activation to integration here before the next one arms. Two waves are never in flight at once; two slices of one wave always are.

**Arm the wave.** `oso-state set mode=plan active_slice=wave-<n> verify_green=false repo_path=<absolute path of the main checkout>`, then `oso-state show` and confirm the keys came back before a single worktree exists — step 1's read-back, for step 1's reason. The WAVE is what the edit gate is armed with rather than a slice: that gate reads one session-global `active_slice` and cannot see which worktree an edit lands in, so every applier of the wave writes under that one armed name. `repo_path` is the fourth key and the teardown's only input — your host's teardown reads it to run `git worktree remove` and `git worktree prune` in the repo the worktrees were cut from, which is how a wave that never integrates is still cleaned up. Absolute, never relative: that teardown runs in no working directory of yours.

**Cut one worktree per slice.** Each from WAVE START, never the change's own CHANGE BASE past the first wave: `git -C <main checkout> worktree add -b oso/<change>/<slice> <worktree root>/<slice> <wave start>`. Wave 1's WAVE START is the main checkout's own HEAD the moment wave 1 arms — CHANGE BASE §3 recorded when no wave 0 ran; wave 0's own landing commit when it did, since the design-foundation slice is the one slice the orchestrator commits directly to the main checkout rather than through step 4's applier/verifier loop. Every later wave's WAVE START is the commit the previous wave's integrator left behind (below) — cutting from CHANGE BASE instead would hand a later wave a tree missing every earlier wave's own landed work, so a slice depending on one would fail for a reason no slice's diff explains. The WORKTREE ROOT is your host's and the reference file spells it — a path spelled any other way is a path the teardown never finds. Record each creation with `oso-state event worktree-created "<the worktree path>"`: a worktree is neither a tool call nor a state write, so nothing else in the harness can put it in the audit. A wave WIDER than the concurrency cap (§4, default 4) runs in BATCHES — cap slices at a time through apply → verify → commit, then the next batch — and integrates ONCE, at the end, since a wave integrated twice would verify its second batch against a tree the first batch's merge had already moved.

**Launch the appliers — N of them, read before anything moves, in ONE message.** A launch whose result you have not read is still a step you have not run, however your host delivers N results, which is the reference file's to state. Each payload is step 2's slice assignment plus the two coordinates that place the work and the one fact that changes how it runs — that slice's own WORKTREE PATH, SLICE START (the same WAVE START its worktree was cut from, since a fresh worktree holds nothing before that cut), and that the slice runs in PARALLEL. That fact is what makes the applier skip its own self-check, since N project bars on one machine contend on ports, test databases, build caches and lockfiles that separate worktrees do not isolate. A `blocked` report takes step 2's route unchanged, and the fresh applier goes back into that same worktree; its siblings never feel it.

**Verify each slice, then the GREEN WINDOW.** Launch `oso-verifier` once per slice with step 3's payload — the slice criteria, the zero-warnings commands from the ledger, the rubric path (`_shared/rubric.md`), the ledger decisions relevant to that slice. Add that slice's WORKTREE PATH as the tree it runs every check in, and SLICE START (that same WAVE START) as what the diff is judged against. These go in one message too, unless the concurrency answer below says this project's bar cannot be run N times at once. Then, only on one slice's `pass` and one slice at a time, three commands with nothing between them:

- `oso-state set mode=plan active_slice=wave-<n> verify_green=true`
- `git -C <that slice's worktree> add -A` and `git -C <that slice's worktree> commit` — that slice's work, on its own branch, in its own worktree
- `oso-state set mode=plan active_slice=wave-<n> verify_green=false`, which re-arms the wave

That window exists because both layers of the commit rail read ONE session-global `verify_green` and neither can see which worktree a commit comes from — the reference file names the two layers. While the window is open the rail is open SESSION-WIDE: any commit, from any tree, in that turn, clears both layers. The only thing that pays for that accidental-bypass window is keeping it as short as those three commands allow — no verifier, no applier, no operator question, no second slice's commit inside one opening.

**The all-green barrier.** A wave integrates only when EVERY slice in it is green. A red slice holds the wave: it loops apply → verify inside its own worktree while its green siblings wait, already committed. No sibling's worktree is torn down while any slice of the wave is still working, because the integrator is handed each slice's worktree path and removes them itself; until it does, that tree is where the operator can read what a slice actually did.

**Merge the wave.** Every slice green and committed, launch the `oso-integrator` agent with the wave and nothing else, and read its report before anything moves: each slice's branch `oso/<change>/<slice>` beside the worktree path it ran in, in the order they merge, and WAVE START — the commit in the main checkout the wave lands on. The integrator runs on the model the profile names for its role, named in the Launching milestone. It merges one branch at a time and judges nothing; on a clean run (`status: done`) its report names the commit the main checkout's HEAD reached once every branch merged — hold that value, it is the next wave's own WAVE START. Its last act is deleting the wave's branches and removing the worktrees they ran in, and the flow continues to the integration gate below.

**When the integrator returns `status: blocked` instead** — the wave payload you built does not match what git actually holds: a branch it cannot find, a worktree path that is not a worktree, or a slice you recorded green whose branch carries no commit. This is never one of the wave-failure classes below — it is your own bookkeeping proven wrong, so report the mismatch to the operator with the exact questions the integrator returned and let them say how the missing state is recovered; once resolved, re-invoke `oso-integrator` with the corrected wave payload. Never guess a subset of the wave to merge in its place.

**The integration gate.** Nothing has judged the tree the wave adds up to, so launch `oso-verifier` on the merged main checkout with its INTEGRATION verdict shape: the merged tree is the goal, the criteria are the project's full bar plus a re-run of every wave slice's regression check with none omitted. The verifier runs on the model the profile names for its role, named in the Launching milestone. The payload carries the zero-warnings commands from the ledger, the rubric path (`_shared/rubric.md`), the ledger decisions the wave implements, the main checkout as the tree it runs in and the wave's WAVE START. Only on its `pass` does the wave close: the worktrees and the branches went with the integrator, so what is left is `oso-state set mode=plan active_slice=none verify_green=true` — the sentinel closing the wave the way step 4 closes a slice. Then mark every slice of the wave `[x]` (`mem_update` on the plan topic key — merge, never overwrite), report the wave to the operator, and arm the next one.

**Failure routing, by class.** Three classes, and none of them borrows another's route:

- **A red slice** — the fail belongs to that slice and stays in its worktree: relaunch the applier there carrying the verifier's findings VERBATIM, every one with its `file:line` and the evidence the verdict recorded for it, and loop apply → verify exactly as step 3 does. A finding grounded in a NO-EXCEPTION rule is no more yours to overrule in a worktree than in the main checkout, and no payload you build for this wave may instruct any judge away from one of those rules. Its siblings run on; nothing about a red slice sends a green sibling back, and the wave waits at the barrier.
- **A merge conflict** — the integrator stops at the first one and returns `status: conflict` with the conflicting files and the slices whose work meets in them. THE ORCHESTRATOR NEVER RESOLVES IT and never edits either side: which side wins is a decision about the change, and decisions are the operator's. It goes to the operator with those files and those slices, the conflicted tree left exactly as git left it, and recorded: `oso-state event merge-conflict "<the branch the merge stopped on>"`. Under a ROADMAP this is the one gate that structurally needs the operator however plainly a tier would have picked a side: carrying a pick out is an edit, and the only writers this flow has are appliers carrying a slice, a cleanup or a judge's finding — never a conflict between two slices. The conflict is queued with those same files and slices, the change is set aside on it, and the tree and both halves' branches stay as this bullet already leaves them.
- **A red integration** — the whole wave returns AS A UNIT. Do not attribute the failure to the slice whose regression check failed: that check names the slice whose BEHAVIOUR broke, never the slice that broke it, so sending that slice back is sending the victim. Report the failing check with the wave's full slice list and the gate's evidence, record it — `oso-state event integration-red "<the failing check>"` — and let the fix enter as a NEW SLICE through the normal apply → verify loop. The route §7 step 3 already gives an `Unimplemented` conformance finding, since work no failing-check gate ever saw may not land under a green.

**The concurrency answer, at the first wave.** §3's Verification row carries as a QUESTION whether this project's bar tolerates being run concurrently, and §4's cap is the lever over it; answering means running that bar N times at once, which is what just happened for the first time. Read the wave's verifications: N at once either came back green, or came back red on something no slice's diff explains — a bound port, a test database two runs share, a build cache, a lockfile one run holds. Write the answer into the ledger's §3 Verification row (`mem_update` — merge, never overwrite), the same shape and the same split as the pin resolution step 2 performs at the first front-touching slice. A bar that does NOT tolerate it changes exactly one thing: the appliers still run in parallel — separate worktrees contend on nothing while files are being written — and the VERIFICATIONS serialize, one verifier at a time in its own worktree, the wave still integrating once.

**The exit back to sequential.** An execution-time offer, never an approval gate. When a wave degrades — conflicts repeating, an integration gate that will not go green, a graph that turned out to be a chain with every remaining wave a width of one — name what you are seeing and offer to finish the remaining slices SEQUENTIALLY, keeping everything already integrated. The operator decides; declining continues in parallel. Same shape as the stop-the-line offer below: name it, offer it, record the answer in the ledger, continue.

Stop-the-line — breakage UNRELATED to the active slice discovered mid-execution (a pre-existing failure, a check that was green turning red for reasons outside the slice) is never fixed in passing: name it, stop feature work, and offer the DEBUG mode; declining is recorded in the ledger and the slice continues. This complements — never replaces — the verifier `fail`/`blocked` paths above; the slice's own red loop stays in §6 as-is. Under PARALLEL, "the active slice" reads as the WAVE: breakage attributable to a SIBLING slice of the wave in flight is the wave's own business and takes the failure routing above — a red slice, a merge conflict, a red integration — and only breakage unrelated to the entire WAVE takes this route.

**Attribution before the route.** That last split turns on a fact nobody has established: whether a red check is the wave's doing or was red before the wave existed. Settling it by reading the diff yourself is the worst option on the table — you wrote the plan the wave executes. So when a wave goes red on a check no slice's diff plainly explains — the integration gate's red, or a check that turns red mid-wave — INVOKE the triage judge first. It runs in its own fresh, isolated context, judges only, and takes in its ARGUMENTS, in the shape its `argument-hint` declares, the failing check with the gate's evidence verbatim, the wave's slices, and WAVE START — never CHANGE BASE, since a breakage an earlier wave already landed into WAVE START is background this wave never introduced. It ends on one of four verdicts and this loop reads all four by name:

- `Triage: attributable` — the wave's own: it takes the failure routing above unchanged, and the fix enters as its own slice through the normal apply → verify loop.
- `Triage: pre-existing` — it predates WAVE START: the stop-the-line paragraph above runs with triage's evidence in hand, so the DEBUG-mode offer names the attribution instead of guessing at it.
- `Triage: skipped — attribution not established` — never read as either answer. It routes to the operator like the verdict above and carries what triage could NOT show as well: the operator is then deciding under the same uncertainty this loop had before triage ran, and an offer that hides that is worse than the offer that never had it.
- `Triage: blocked` — its own launch never reached it whole, a defect in what you handed it, never evidence about the wave: resolve what it names missing and invoke the triage judge again fresh before reading either wave-failure route above.

Triage removes the guessing, never the operator's decision: the offer is still made, declining is still recorded in the ledger, and the wave continues.
