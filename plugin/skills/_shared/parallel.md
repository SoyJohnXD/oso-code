### Parallel — the wave loop

Everything above is the SEQUENTIAL path, one slice at a time in the main checkout. PARALLEL's unit is the WAVE (§4), a set of slices with no edge between any two of them. Each slice runs the four steps above inside its OWN worktree, and one wave goes from activation to integration here before the next one arms. Two waves are never in flight at once.

**Arm the wave.** `oso-state set mode=plan active_slice=wave-<n> verify_green=false repo_path=<absolute path of the main checkout>`, and read the echo for the keys before a single worktree exists. The edit gate is armed with the WAVE rather than a slice: it reads one session-global `active_slice` and cannot see which worktree an edit lands in, so every applier of the wave writes under that one armed name. `repo_path` is the teardown's only input — your host's teardown reads it to run `git worktree remove` and `git worktree prune` in the repo the worktrees were cut from, so a wave that never integrates is still cleaned up. It is absolute, since that teardown runs in no working directory of yours.

**Cut one worktree per slice.** Each from WAVE START, never the change's own CHANGE BASE past the first wave: `git -C <main checkout> worktree add -b oso/<change>/<slice> <worktree root>/<slice> <wave start>`. Wave 1's WAVE START is the main checkout's own HEAD the moment wave 1 arms — CHANGE BASE §3 recorded when no wave 0 ran; wave 0's own landing commit when it did, since the design-foundation slice is committed by the orchestrator directly to the main checkout. Every later wave's WAVE START is the commit the previous wave's integrator left behind (below). The WORKTREE ROOT is your host's and the reference file spells it; any other path is one the teardown never finds. Record each creation with `oso-state event worktree-created "<the worktree path>"`, since a worktree is neither a tool call nor a state write. A wave WIDER than the concurrency cap (§4, default 4) runs in BATCHES — cap slices at a time through apply → verify → commit, then the next batch — and integrates ONCE, at the end.

**Launch the appliers — N of them, read before anything moves, in ONE message.** A launch whose result you have not read is still a step you have not run; the reference file states how your host delivers N results. Each payload is step 2's slice assignment plus that slice's own WORKTREE PATH, SLICE START (the same WAVE START its worktree was cut from), and the fact that the slice runs in PARALLEL. That fact makes the applier skip its own self-check, since N project bars on one machine contend on ports, test databases, build caches and lockfiles. A `blocked` report takes step 2's route unchanged, and the fresh applier goes back into that same worktree.

**Verify each slice, then the GREEN WINDOW.** Launch `oso-verifier` once per slice with step 3's payload — the slice criteria, the zero-warnings commands from the ledger, the rubric path (`_shared/rubric.md`), that slice's DECISION BLOCK, and the `applier_proof` package of exactly its applier's `proof:`, `scan:`, and `decisions_used:` blocks. Add that slice's WORKTREE PATH as the tree it runs every check in, and SLICE START (that same WAVE START) as what the diff is judged against. These go in one message too, unless the concurrency answer below says this project's bar cannot run N times at once. Then, only on one slice's `pass` and one slice at a time, three commands with nothing between them:

- `oso-state set mode=plan active_slice=wave-<n> verify_green=true`
- `git -C <that slice's worktree> add -A` and `git -C <that slice's worktree> commit` — that slice's work, on its own branch, in its own worktree
- `oso-state set mode=plan active_slice=wave-<n> verify_green=false`, which re-arms the wave

Both layers of the commit rail read ONE session-global `verify_green` and neither can see which worktree a commit comes from — the reference file names the two layers — so while the window is open, any commit from any tree clears both. Keep it as short as those three commands allow: no verifier, no applier, no operator question, no second slice's commit inside one opening.

**The all-green barrier.** A wave integrates only when EVERY slice in it is green. A red slice holds the wave: it loops apply → verify inside its own worktree while its green siblings wait, already committed. No worktree is torn down while any slice of the wave is still working; the integrator removes them itself.

**Merge the wave.** Every slice green and committed, launch the `oso-integrator` agent with the wave and nothing else, and read its report before anything moves: each slice's branch `oso/<change>/<slice>` beside the worktree path it ran in, in the order they merge, and WAVE START — the commit in the main checkout the wave lands on. The integrator runs on the model the profile names for its role, named in the Launching milestone. It merges one branch at a time and judges nothing; on a clean run (`status: done`) its report names the commit the main checkout's HEAD reached — hold that value, it is the next wave's own WAVE START. Its last act is deleting the wave's branches and removing their worktrees; the flow continues to the integration gate.

**When the integrator returns `status: blocked` instead** — the wave payload you built does not match what git actually holds: a branch it cannot find, a worktree path that is not a worktree, or a slice you recorded green whose branch carries no commit. This is never one of the wave-failure classes below: report the mismatch to the operator with the exact questions the integrator returned, and once they say how the missing state is recovered, re-invoke `oso-integrator` with the corrected wave payload. Never guess a subset of the wave to merge in its place.

**The integration gate.** Nothing has judged the merged tree, so launch `oso-verifier` on the merged main checkout with its INTEGRATION verdict shape: the merged tree is the goal, the criteria are the project's full bar plus a re-run of every wave slice's regression check with none omitted. The verifier runs on the model the profile names for its role, named in the Launching milestone. The payload carries the zero-warnings commands, the rubric path (`_shared/rubric.md`), the ledger decisions the wave implements, the main checkout as its tree and the wave's WAVE START. Only on its `pass` does the wave close, with `oso-state set mode=plan active_slice=none verify_green=true` — the sentinel closing the wave the way step 4 closes a slice. Then mark every slice of the wave `[x]` (`mem_update` on the plan topic key — merge, never overwrite), report the wave to the operator, and arm the next one.

**Failure routing, by class.** Three classes, and none of them borrows another's route:

- **A red slice** — the fail belongs to that slice and stays in its worktree: relaunch the applier there carrying the verifier's findings VERBATIM, every one with its `file:line` and the evidence the verdict recorded for it, and loop apply → verify under step 3's two-round cap, diagnosis, routes and empty-result rule. The wave's `active slice` row counts the whole wave, so each red slice counts its own rounds. A finding grounded in a NO-EXCEPTION rule is no more yours to overrule in a worktree than in the main checkout, and no payload for this wave may instruct any judge away from one. Its siblings run on; the wave waits at the barrier.
- **A merge conflict** — the integrator stops at the first one and returns `status: conflict` with the conflicting files and the slices whose work meets in them. THE ORCHESTRATOR NEVER RESOLVES IT and never edits either side: which side wins is the operator's decision. It goes to the operator with those files and slices, the conflicted tree left as git left it, and recorded: `oso-state event merge-conflict "<the branch the merge stopped on>"`. Under a ROADMAP the conflict is queued with those same files and slices and the change is set aside on it, since no tier can carry a pick out: the only writers this flow has are appliers carrying a slice, a cleanup or a judge's finding.
- **A red integration** — the whole wave returns AS A UNIT. Do not attribute the failure to the slice whose regression check failed: that check names the slice whose BEHAVIOUR broke, not the slice that broke it. Report the failing check with the wave's full slice list and the gate's evidence, record it — `oso-state event integration-red "<the failing check>"` — and let the fix enter as a NEW SLICE through the normal apply → verify loop. It is the route §7 step 3 already gives an `Unimplemented` conformance finding.

**The concurrency answer, at the first wave.** §3's Verification row carries as a QUESTION whether this project's bar tolerates being run concurrently, and §4's cap is the lever over it. Read the first wave's verifications: green, or red on something no slice's diff explains — a bound port, a shared test database, a build cache, a lockfile. Write the answer into the ledger's §3 Verification row (`mem_update` — merge, never overwrite). A bar that does NOT tolerate it changes exactly one thing: the appliers still run in parallel, and the VERIFICATIONS serialize, one verifier at a time in its own worktree, the wave still integrating once.

**The exit back to sequential.** An execution-time offer, never an approval gate. When a wave degrades — conflicts repeating, an integration gate that will not go green, a graph that turned out to be a chain with every remaining wave a width of one — name it and offer to finish the remaining slices SEQUENTIALLY, keeping everything already integrated. The operator decides, recorded in the ledger; declining continues in parallel.

Stop-the-line — breakage UNRELATED to the active slice discovered mid-execution (a pre-existing failure, a check that was green turning red for reasons outside the slice) is never fixed in passing: name it, stop feature work, and offer the DEBUG mode; declining is recorded in the ledger and the slice continues. This complements — never replaces — the verifier `fail`/`blocked` paths above; the slice's own red loop stays in §6 as-is. Under PARALLEL, "the active slice" reads as the WAVE: breakage attributable to a SIBLING slice of the wave in flight takes the failure routing above — a red slice, a merge conflict, a red integration — and only breakage unrelated to the entire WAVE takes this route.

**Attribution before the route.** Whether a red check is the wave's doing or was red before it is not settled by reading the diff yourself, since you wrote the plan the wave executes. So when a wave goes red on a check no slice's diff plainly explains — the integration gate's red, or a check that turns red mid-wave — INVOKE the triage judge first. It runs in its own fresh, isolated context, judges only, and takes in its ARGUMENTS, in the shape its `argument-hint` declares, the failing check with the gate's evidence verbatim, the wave's slices, and WAVE START — never CHANGE BASE, since a breakage an earlier wave landed is background this wave never introduced. It ends on one of four verdicts and this loop reads all four by name:

- `Triage: attributable` — the wave's own: it takes the failure routing above unchanged, and the fix enters as its own slice through the normal apply → verify loop.
- `Triage: pre-existing` — it predates WAVE START: the stop-the-line paragraph above runs with triage's evidence in hand, so the DEBUG-mode offer names the attribution instead of guessing at it.
- `Triage: skipped — attribution not established` — never read as either answer. It routes to the operator like the verdict above and carries what triage could NOT show as well, since the operator is deciding under the same uncertainty this loop had before triage ran.
- `Triage: blocked` — its own launch never reached it whole, a defect in what you handed it, never evidence about the wave: resolve what it names missing and invoke the triage judge again fresh before reading either wave-failure route above.

**Standing worktrees at §0's resume.** Run `git -C <main checkout> worktree list` and report every worktree of this change still standing, each naming the slice its branch (`oso/<change>/<slice>`) holds. What becomes of them is the operator's; the close below clears them.

**The teardown at §7's close.** A change that ran in waves first removes any worktree of this change still standing (`git -C <main checkout> worktree remove <path>`, never `rm -rf`), then runs `git -C <main checkout> worktree prune`, then deletes each branch (`git -C <main checkout> branch -d oso/<change>/<slice>` — never `-D`, never a force). A refused removal is uncommitted work from a wave that never integrated; a refused delete is the only copy of that slice's committed work. Name either to the operator with its slice — never force it.
