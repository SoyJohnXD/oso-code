# Unattended execution — AUTO, its park, and its ceiling

Read from the start of every PLAN-mode run, never conditionally the way `_shared/parallel.md` is: AUTO can arm at any point, mid-execution, on a single operator instruction, so the flow has to know these rules before that instruction ever arrives. Gathered here rather than cut from one place: the ground rules' own AUTO bullets, the Ceiling field §0 asks apart from Behavior, what §4's execution-disposition question and §5's own record and initialize add, and what §6 and §7 do with a commit and a close under AUTO.

## The ground rules' own AUTO bullets

- The AUTO disposition's own marker is the one thing written BESIDE the `mode`/`active_slice`/`verify_green` triple instead of over it: a write naming the marker alone leaves all three keys exactly as they stood, which is why the bullet below spells it alone wherever it arms or flips it.
- A ROADMAP's child has no operator to wait for at all, and that is absence's FIRST producer. This flow's own AUTO run is the SECOND: a change executing under AUTO, whose operator exists and has stepped out, which costs this flow exactly what having none costs that child. AUTO is a DISPOSITION of the run — never an invocation argument, never a fifth mode — armed as the second question of the execution-mode round §4 asks, or by explicit operator instruction at any point this flow reaches, mid-execution included ("sigue en auto, voy a salir"), and disarmed the same way; every flip is recorded DATED in this change's ledger (`mem_update` — merge, never overwrite), and the flip itself is the consent, so nothing further is asked before it takes effect. Phases 1–5 always run with the operator: AUTO governs §6 and §7 alone. The disposition is RECORDED in that ledger and in the index row's `NEXT:` line, and it is ARMED on the runtime state beside them, one marker with three values: `oso-state set auto=running auto_change=<change-slug>` at the flip that arms it, `auto=parked` at the park the bullet below defines, `auto=done` at §7's close — `mode=plan` throughout and the same three keys §5 and §6 already write, the marker beside that triple and never over it. What it buys is what a ledger line cannot: a host whose delivery contract carves an unattended run out of its turn-ending rule reads that marker to know this run is one, and whatever rails that host arms while nobody is watching arm on the same value — the platform file names both, and neither is this body's to spell. Every milestone this run reports under `_shared/reporting.md` is ALSO appended full-text with `oso-state journal "<the milestone as it was written>"`, the per-change journal `auto_change` names, because the live stream of a run nobody watched is not a record and that file is. So a compaction mid-run costs the WINDOW and not the POSITION: the position is re-read from the `oso/index` row's `NEXT:` line, from `oso-state show` and from that journal, prompted by whatever re-anchor the host has and the platform file names. Whoever resumes a parked run is present by definition and §0's own resume path is the resume path. What answers a decision in the operator's place while it is on is the ROADMAP mode's own §2 autonomy policy, named here rather than copied and read at THIS change's scale: its three tiers, its irreversibility bar and its never-solo list entire, with this change's own frozen ledger answering first where that policy reads a global ledger and a child's — one ledger instead of two, and nothing else about it moves. An operator MESSAGE while AUTO is on disarms nothing: an answer to a question this flow queued is consumed as operator input and the run continues under AUTO, a comment is attended and the run continues, and only an explicit resume instruction — "retomo yo" and its kin — hands the flow back, so neither silent failure stands, AUTO dying on a glance nor the operator's return going unheard. Wherever `bodies/plan.md` reads "under a ROADMAP", a change executing under its own AUTO disposition reads the same way, with exactly TWO substitutions and the bullet below carrying both.
- The TWO substitutions with which a run under its own AUTO reads the set-aside routine `bodies/plan.md`'s policy bullet describes, and there is no third: what a child queues for that mode's §5, this run queues for its OWN final report — the three parts §7 delivers at the run's end — and where the ROADMAP mode's chain arms the next child behind a set-aside one, this run PARKS. Parking is the same set-aside routine `bodies/plan.md`'s policy bullet describes, with its own last step replaced: it reports BLOCKED carrying the queued question or questions as they stood, delivers that same final report, writes the set-aside state over whatever the stopped slice or wave left armed with the disposition's own marker flipped beside it in that one write (`oso-state set mode=plan active_slice=none verify_green=false auto=parked`), and ends the turn there. That marker is what tells a park from a stall ON DISK rather than by inference: a run parked at a question reads `auto=parked` and a run that simply stopped mid-milestone still reads `auto=running`, so a host's unattended rails carry the second on and let the first rest. The park is also one of exactly two deliveries an unattended run still ENDS THE TURN on, the final report §7 delivers being the other — a park is the run handing itself back, never a milestone going by. `oso-state clear` is no more run here than in that routine, and for one reason more: this run expects resumption, so its position stays durable in this change's ledger, in its plan topic and in its `oso/index` row, and the SessionStart stale-state notice already names this mode's own re-invocation, spelled for the host it fires on, as the way back through §0 — where the operator who resumes is present by definition. A park is an END OF THE TURN and never an abandonment.
- AUTO's CEILING is how far a run reaches without another person, and it is contract rather than improvisation: this machine and the environments the change's own bar reaches from it — local, and STAGING where the project has one — plus the branch the run works on and the PR that finishes it. The branch is cut at §5's initialize, beside the write that arms the marker: a run under AUTO works on `oso-run/<change>`, the DEFAULT branch being the case that cut exists for, and the name sits deliberately outside the slice namespace `oso/<change>/<slice>`, since git cannot hold `oso/<change>` as a ref while `oso/<change>/<slice>` is a directory of refs. Every commit §6 lands reaches that branch — step 4's directly, a wave's through the integrator's merge into the main checkout — and §7 step 8 pushes it and opens the PR that closes the run. There the reach ends: the MERGE of that PR, a release and a PRODUCTION deploy are on the never-solo list the policy above binds this run to, refused however plainly a tier would have taken them. What the approval that armed the run bought is a branch and a PR somebody reads, never a change standing in front of people who never approved it. Three of the facts that ceiling rests on are the PROJECT's rather than this run's — where staging is and how it is reached, what production is and is therefore never touched, and the branch a pull request opens against — so they live in the per-project record §0 reads (`oso/preferences`) and are asked at the FIRST ARMING IN THIS PROJECT, never at that first plan. A record already carrying them is read silently and nothing is asked; missing them, ask ONE round for the three through your host's question tool, inside the per-round cap the platform file names, and write the answers into that SAME record with `mem_update` (merge, never overwrite). Then write the MIRROR, because a record only this flow reads stops nothing a hook has to stop: the production answer distilled into deny patterns, ONE ERE PER LINE, appended to `$OSO_STATE_DIR/deploy-deny/<digest>.patterns` — `<digest>` naming this repository exactly as its own state file `~/.local/state/oso-code/<digest>.state` already names it — and written through SHELL, this flow's own hands, creating that directory with `mkdir -p` before the append, since no `oso-state` command writes that file or makes the directory it sits in. A patterns file that cannot be written is REPORTED, with what could not be written and where, never skipped in silence; the gate's own built-in refusals stand either way, and what the mirror adds is this project's routes on top of them. NO RECORD AND NOBODY TO ASK — a run resumed on a machine where those fields were never filled — arms no AUTO at all: the run proceeds attended-shaped, or parks its finish as the named pending §7 step 8 already defines.

## The Ceiling field, asked apart from Behavior at §0

- **Ceiling — asked at the FIRST AUTO OR ROADMAP ARMING in this project** and never in the round §0 asks for Behavior: the STAGING ROUTE (whether this project has one, and how it is reached), the PRODUCTION ROUTE (what an unattended run never touches), and the PR BASE BRANCH this repository's pull requests open against. A project that never runs unattended is never asked for its production route, which is the whole reason these three sit outside the first-plan round; the ground rules' ceiling bullet owns that ask and the mirror it writes beside the record.

A ceiling field updates through a natural-language request from the operator, applied with `mem_update` — merge, never overwrite — and confirmed, no ceremony.

## Choosing AUTO at §4's execution-disposition question

NORMAL is the default and the recommendation: AUTO buys nothing for an operator who is sitting here, and the one about to leave is the one who takes it. Never re-ask what the ledger already answers — an operator who said auto earlier, at any point this flow has reached, has answered this question, and it is skipped with their answer recorded exactly as §4's execution-mode question is.

An answer of AUTO is RECORDED here and ARMED at §5: this phase writes no runtime state at all, so the marker the ground rules define (`auto=running auto_change=<change-slug>`) rides §5's own initialize, and a flip taken later — mid-execution, by instruction — arms it where it is taken. An AUTO answer also reaches for the CEILING fields the ground rules define: where this project's `oso/preferences` record already carries the staging route, the production route and the PR base branch, they are read silently; where it does not, that ask is its OWN round after this one — never a third and a fourth question bolted onto this one, since the cap the platform file names is a cap — and its answers go back into that record with the mirror the ceiling bullet requires.

## §5's own AUTO writes

The `NEXT:` line also carries `AUTO` beside the position while that change runs under the AUTO disposition, written and dropped with the flip that arms or disarms it (e.g. `NEXT: plan2-purga slice 3/6 AUTO → then roadmap Plan 3`).

At §5's initialize — `oso-state set mode=plan active_slice=none verify_green=false` — plus `auto=running auto_change=<change-slug>` in that same write where §4's disposition answer was AUTO, which is where that answer stops being a ledger line and starts being a marker. That answer also cuts the run its own branch here, beside the marker: `git -C <main checkout> checkout -b oso-run/<change>`, cut from wherever the checkout stands and the DEFAULT branch being the case it exists for, is what §6's commits then land on and what §7 step 8 pushes — skipped only on a RESUME, where `git -C <main checkout> rev-parse --abbrev-ref HEAD` already reads that same name because this run cut it before. The namespace is not decoration: where a host arms an unattended rail on this marker, that rail denies a push of any other name while the run is in flight, and the platform file names it. Record the branch in the ledger (`mem_update` — merge, never overwrite), because the close pushes a recorded name rather than whatever the checkout happens to say by then.

## §6's own AUTO commit

Under AUTO the slice's commit lands on the `oso-run/<change>` branch §5 cut, the branch that close pushes whole.

## §7's own AUTO close

A run whose operator flipped AUTO owes them one report at its END, and owes it whichever end the run reached — this close, or the park the ground rules define. Deliver it in the ROADMAP mode's own three parts and no fourth: what was decided for them and on what rationale, every answer naming the tier that took it; what was deferred and why, each item as the question it was; and what awaited their hand, the pendings and the named residuals nothing they answer releases.

At this close the two are SEQUENCED and the order is the whole of whether that report is read: DISARM first — `oso-state set auto=done`, a tool call — and deliver the report after it, as that same turn's trailing text. Text that follows a tool call is delivered where text that precedes one may not be, so the disarm is what makes the report the turn's last word; and a run still marked running is a run a host's unattended rails carry on rather than let stop, which is the same sentence read from the rail's end. It is the LAST thing this close does, after step 8 and never before it: nothing is disarmed over work still to come.

Under an UNATTENDED run PUSH and PR are the FINISH instead — the thing the plan approval that armed it chartered — and it runs after step 7's green: push the branch §5 recorded (`git -C <main checkout> push -u origin oso-run/<change>`), then open the PR against the base the per-project record (`oso/preferences`) holds for this repository, through `gh pr create` or whatever route this host has for opening one, and record the branch, the PR and its base in the run journal and in the final report above. The reach stops at that PR: its MERGE, a release and a production deploy are on the never-solo list the ground rules bind this run to, and no tier takes one. Where the repository has no remote, or the push or the PR call fails, the finish is PARKED as a named pending in that final report — the branch, its commits and what stopped them — never a silent skip and never a retry loop; the close still disarms and delivers exactly as above.
