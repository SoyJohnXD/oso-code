# Roadmap mode

Host precondition: this operator-only skill starts only when Codex's active
collaboration mode is `Plan`, because §1 plans the queue with the operator
through `request_user_input`, which this host exposes only there. If it is not,
stop immediately and tell the operator to enter `/plan` (or use Shift+Tab), then
invoke `$oso-code:roadmap` again. Never imitate the transition by printing
`/plan`, and do not begin §1 in Default mode. No installed hook gates this
invocation: `UserPromptSubmit` refuses `$oso-code:plan` outside Plan Mode and no
other skill invocation, so this instruction is the whole of that boundary.

The flow that follows this preface is the same on every host this harness runs on. It opens by pointing you at `references/codex.md` — what it leaves to this host: how far the chain runs unattended, the paths it resolves, where each child still waits for the operator, and the state command every runtime write of the chain runs under, which that file routes to plan's own reference file rather than spelling twice.


# Roadmap mode

Guided flow for a QUEUE of changes, decided once and run to the end without a second sitting. The operator decides the queue and the decisions that shape it up front; the flow then carries each child as far as those decisions carry it — to its close, or to the SET ASIDE §3 describes when one they never answered surfaces. Read your platform's own reference file beside this one (`references/<host>.md`) now — it is what this flow leaves to the host: how far the chain runs unattended, the approval gate, the paths it interpolates, the state command. Wherever this flow says "your host", that file is the answer.

## Ground rules for the whole flow

- Every child is a PLAN-mode change — a sequence of substantial changes decided together, never a list of small fixes with a queue drawn around them. An ask that belongs in QUICK or DEBUG belongs there whether or not it arrived beside four others.
- The exchange with the operator is §1 through §3; everything after runs on what that exchange recorded, without coming back to ask again — the whole trade this mode offers.
- ONE approval covers the whole roadmap — the planning behind it and the execution of every child in it. Where a host's own rail needs more than that one, the reference file states where the chain stops and what releases it.
- Operator-facing content — the queue as it is planned, the approval document, the presence phase — is delivered under the reference file's delivery contract.
- Report every arm, every delegation launched, every verdict, every child closed under the milestone contract at `_shared/reporting.md`, read ALWAYS by this flow. An unattended run is the case that contract was written for: nobody is in the exchange, so what the flow says as it goes is the whole of what the operator gets. Which moments may INTERRUPT them, rather than merely reaching the stream they read on return, is §5's to fix, and it names three; a child closing is deliberately not one of them.

## 1. The queue — planned with the operator

Three artifacts come out of this phase, and §3 approves them together:

- **The children, in order** — each one a change the PLAN mode could take on its own.
- **The global ledger** — the decisions that hold across the whole roadmap, taken here once instead of once per child.
- **Each child's own important decisions** — the ones that would otherwise surface mid-execution with nobody there to answer them.

The exchange runs in question rounds shaped the way the PLAN mode's own decision rounds already require — 2–4 concrete options with their tradeoffs, your recommendation first with why it wins and whether it is current standard practice, current docs checked before recommending anything that turns on an external library. Round size and the asking tool are the reference file's.

**Each child carries three fields, and a child missing one is not queued yet.**

- **Intent** — what that change delivers, one abstraction level above code. Settled HERE: the PLAN mode's §1 iterates an intent until the operator approves it, and a child planned unattended has nobody there to give that approval, so this exchange gives it and §3 is what approves it.
- **Mode** — PLAN. The only mode this version queues; an ask that belongs in QUICK or DEBUG meets the answer the PLAN mode's own phase 1 gives it — say so, offer that mode, and the operator decides, rather than carrying it into the queue to be discovered when the chain reaches it.
- **Whether it already carries an approved plan** — a child whose ledger was frozen, whose slices were cut and whose plan was approved in an earlier PLAN-mode run executes as approved; a child arriving with an intent alone is planned unattended under §3's approval. Recorded here, since which of the two a child is decides how much work stands in front of it.

**The global ledger** holds a decision the operator would otherwise take again in every child's rounds: the same answer to the same core lens — Contracts, Architecture, Errors, Verification, Reuse, the PLAN mode's own §3 invariant core — across all or most of the children. An entry that applies to most of them names the ones it does not.

What a global entry then does to a child's own planning has three parts and no fourth. **Inheritance** — a pre-answered question is recorded INHERITED, naming the global entry it came from, and is never re-derived or re-asked. **Precedence** — a per-child decision from this phase overrides a global entry for that child alone, the narrower decision winning because it was taken about that child specifically. **Reconciliation** — a child's own evidence contradicting an inherited entry is never silently resolved either way, and §2 is what answers it, not this phase.

**Where this phase's output lives**, under the index format standard the PLAN mode's §5 states — this mode adds no second standard and spells no key any other way. `{roadmap}` is a short kebab slug, the way `{change}` is:

- `oso/{roadmap}/ledger` — the queue in order with each child's three fields, the global ledger entry by entry with each entry's scope, and each child's own decisions. Saved once at this phase's exit — `mem_save(title: "oso/{roadmap}/ledger — {human description}", topic_key: "oso/{roadmap}/ledger", type: "architecture", capture_prompt: false, content: the queue + the global entries + each child's decisions)`, content and title in English — and every later touch is a `mem_update` that merges, never overwrites. §2's policy joins it at that same key.
- `oso/index` — one row for the roadmap, status `roadmap`, written at §3 when the approval makes the roadmap real. It lists every child in run order by the LITERAL topic key that child's own flow writes (`oso/{child}/plan`), never a wiki-link. A child the chain has not reached carries no such observation yet, and the ledger topic above is that child's record until its own flow writes one. The `NEXT:` line is where the roadmap's position lives.
- Each child keeps its normal per-change topics — `oso/{child}/ledger`, `oso/{child}/plan`, `oso/{child}/summary` — plus its own index row, all written by its own flow. The parent adds a row and replaces none of theirs: `roadmap` marks a row as a parent rather than reporting progress, so how far the roadmap has got reads off the children's rows and that `NEXT:` line.

Exit: every child carries its three fields, every global entry carries its scope, every child carries its own decisions or an explicit none, and the ledger observation is saved. Nothing is approved yet — §2 declares the policy over this queue, and §3 is the one gate.

## 2. The autonomy policy

A decision will surface after the operator has gone; an unattended chain guarantees it rather than risking it. The policy answers such a decision, and it is DECLARED here, before the approval, so the answer is one the operator agreed to rather than one the flow improvised on their behalf.

It has two outcomes and no third. A decision the policy resolves is taken and RECORDED AS DELEGATED, naming the policy that decided it. A decision that structurally needs the human is QUEUED for §5 and the chain moves on — queuing never blocks it, and nothing queued is answered by guessing.

**The policy answers the residue, never the record.** §1's decisions answer first — a per-child decision, then a global entry a child records as INHERITED — and the ladder below is reached only where neither does. A RECONCILIATION (§1's third part) is never a tier's to take: an inherited entry a child's own evidence contradicts is two answers, not a missing one, and it is queued like everything else this policy will not decide.

**Three tiers, and a tier is reached only when the one above it has nothing to say.**

- **The flow's own recommendation, first.** Put the way any decision round already must — options with their tradeoffs, the recommendation FIRST with why it wins and whether it is current standard practice, current docs checked before anything that turns on an external library or API is recommended. This tier invents nothing; running unattended changed only who was there to read what those rounds produce anyway. A recommendation you could not justify in those same terms, on the evidence in front of you, is not one — the tier is silent rather than dressing a coin toss as a recommendation.
- **Current standard practice, next.** Where the tradeoffs do not separate the options, what current practice standardly does in that case decides — checked against a current source (the harness's own docs route for a library, framework or API, official documentation otherwise) and CITED in the delegated record below. Where no source is reachable at all, the argument is written out instead, marked UNSOURCED.
- **Simplest for the operator, last.** Where practice standardizes nothing here, or standardizes two things equally, the option that costs the operator least to live with wins: fewest moving parts, least to learn, least to keep working. Simplest to IMPLEMENT is a different question this tier never answers.

Record the answer in vocabulary that already exists: the delegated mark the PLAN mode's §3 writes for a decision handed to the flow, its rationale naming the tier that decided it and the BASIS it stands on — the source it cites, or the unsourced argument where none was reachable. Nothing here adds a second shape for recording one.

**The irreversibility bar.** A tier's confidence is not an undo, so one class of decision is refused however plainly a tier would have answered it: if this answer is wrong, does undoing it need more than an edit and a re-run in this repository? Anything whose undo needs a restore, a refund, a revocation, a retraction, or another person is over the bar — a destructive migration, deleted data, spend or a commitment to spend, an external signup, or whatever else is irreversible or externally visible. Such a decision DEFERS instead of resolving: it takes the queued outcome, and no tier is consulted for it. The bar governs what this POLICY decides and never what the operator already decided — a destructive step §1's ledger settled is their own decision, and carrying it out is what §3's approval covers.

**The never-solo list, fixed at five.** None of these is a new refusal; each is already refused where it lives, and the list stands here so a declared policy can never be read as covering them:

- **A push to a SHARED branch, a PR MERGE, or a release.** What an unattended run does with its own work is not on this list: the PLAN mode's close pushes the CHANGE BRANCH that run worked on and opens the PR that finishes it — the branch leaves the machine once, at that close. The refusal starts one step past it: a push onto a branch other work already builds on, the MERGE that makes the change everybody's, and the release either reaches.
- **A production deploy.** An unattended run reaches this machine and the environments the change's own bar names — local, and staging where the project has one — and its reach ends there; production is nobody's tier to take, however plainly one would have taken it.
- **A ledger amendment.** A frozen decision is amended through that mode's conformance triage, where the operator — never the flow — picks the amendment over the other reading. Where a host's own rail lets an approved plan be amended at all, the operator's request or their one-line confirmation is what authorizes it, never a finding of the harness's own.
- **Accepting a security residual.** The security review at that same close ends in fixes the operator accepted or in a residual the operator explicitly accepted; both are theirs to give.
- **A forced deletion.** That close names a removal git refuses to the operator instead of forcing it, and takes a branch out with `-d` and never `-D`.

None of the five is a tier's question: each takes the queued outcome. What queuing then costs the child it surfaced in is §3's last bullet's to say, and it is said once, there.

Once declared, save the policy into the roadmap's ledger topic at §1's key — a `mem_update` that merges it in beside the queue and overwrites nothing there.

Exit: the three tiers, the bar and the never-solo list are declared, and the policy sits in the roadmap's ledger topic beside the queue. Nothing has been decided under it yet — the first decision it takes belongs to a child, past the one gate §3 is.

## 3. Approval — once, for the whole roadmap

§1's queue and §2's policy go to the operator as one document, and their approval covers the planning behind it and the execution of every child in it. What the approval gate IS on this host, and what passes it, is the reference file's.

**What that one approval authorizes:**

- **Planning every child that arrived with an intent alone** — unattended, through the PLAN mode's own phases, on the intent §1 settled and against the global ledger §1 froze. That mode's freeze needs no exception carved for this one: its reconciliation checklist asks every question to map to a ledger decision, a delegated mark or a reasoned N/A. Both answers this mode supplies are already one of those — an inherited entry is a ledger decision recorded as inherited, and a decision §2's policy took is the delegated mark that phase already writes. §2's other outcome supplies no answer to map, so that checklist refuses the freeze over it exactly as it would with the operator in the room; the last bullet below is where that refusal lands.
- **Executing every child** — the ones planned under this approval and the ones that arrived carrying a plan of their own already approved, in the order §1 recorded.
- **Deciding exactly what §2's policy resolves**, recorded as delegated and naming the policy that decided it.

**What it does not:**

- **A child, or an intent, this document does not carry.** A queue that changes materially after presentation — a child added, an intent redrawn, a global entry reopened — invalidates the approval: re-present the whole document and pass the gate again, the rule the PLAN mode's §5 states about its own plan.
- **A child's own plan document.** Every child planned here still builds and delivers the Repaso-headed plan document the PLAN mode's §5 produces — it is what the operator reads to see what this approval actually bought. Where a host's rail stops at each child, that document is what the rail waits behind; the reference file states where it stops and what releases it. This approval covers that document's approval where the host asks for none; it never replaces the document. A child the last bullet below sets aside while it was still being planned is the one exception, and it is no gap: nothing was frozen there, so there is nothing to present and nothing to execute.
- **A decision §2's policy cannot resolve.** That one is queued for §5 and the chain moves on. An approval already given is no licence to answer it, so what a queued decision costs is paid by the CHILD it surfaced in, never by the chain, which arms the next one either way:
  - **Queued while a child is still being PLANNED**, it stops that child where it stood: the checklist above refuses the freeze, this approval authorizes no way around that refusal, and the child is SET ASIDE — carried no further, never executed — while the chain arms the one behind it.
  - **Queued while a child is EXECUTING, over something its progress does not wait on**, it costs that child nothing. The PLAN mode's own execution-time decisions of that shape are OFFERS — stopping the line for breakage the slice did not cause, the exit back to sequential, the security review at the close — and an offer nobody is there to take is an offer not taken, which that mode's own route for a declined offer already covers. The child runs on to its close, no frozen decision of its ledger is reopened, and the item travels to §5.
  - **Queued while a child is EXECUTING, over something its progress DOES wait on**, it cannot be free. A question the frozen ledger does not answer stops the slice that hit it, and a second attempt over that same unanswered ledger stops in the same place; a divergence between the code and a decision is the operator's to read. Such a child is SET ASIDE mid-execution: the slices it already landed stay as its own execution left them — committed, where that child's ledger kept per-slice commits on — the ones behind them are never executed, and the chain arms the next child. Which of the PLAN mode's own routes carries such a child there is that mode's to state.

  Every decision queued here, and every child a queued decision set aside, reaches §5.

Passing the gate is what makes the roadmap real, so it is here that `oso/index` gains the roadmap's row, in the shape and the vocabulary §1 spells for it.

## 4. The chain

Each child runs as its own PLAN-mode change — planned, executed and closed, or set aside at whichever of those a queued question reached it in — and the next one arms only once the one before it has closed or was set aside, the way §3's last bullet describes.

**Arming a child** hands it four things and nothing this phase invents. The INTENT §1 settled, which that child's own phase 1 takes as approved instead of iterating one. Its own decisions from §1, which its decision rounds record rather than re-ask. The global entries whose scope covers it, which its ledger records as INHERITED naming the entry each came from. And the policy §2 declared, which is what answers a decision its rounds would otherwise put to somebody who is not there. The arming also tells it that it IS a child — the PLAN mode's ground rules ask this section for exactly that. And it tells it which of §1's two kinds it is: a child carrying an approved plan enters that mode's execution with its ledger frozen and its slices already cut; a child arriving with an intent alone runs those phases here, unattended, under the one approval §3 gave.

**Running it and reaching a disposition.** The child runs the PLAN mode start to finish; nothing about it is reimplemented here, and the only thing this chain reads out of it is which of TWO words it ended on. CLOSED is that mode's §7 reached — its own machine entry condition, its sweep's exit bar, its green — and SET ASIDE is the disposition §3's last bullet describes, at either of the two points it names. There is no third word: a child that is neither is a child still running, and nothing else arms while one is. Whichever it ended on is recorded in the roadmap's ledger topic against that child (`mem_update` — merge, never overwrite), with the reason where the word is SET ASIDE. The `NEXT:` line of the roadmap's `oso/index` row then moves to the child behind it — where §1 put the roadmap's position, and the only place a later session reads it from.

**The tree handoff, and it is read before EVERY arming.** The chain hands the next child ONE working tree in one repository: its SLICE START is `HEAD`, its step 4 runs `git -C <main checkout> add -A`, and its verifier judges `git -C <main checkout> diff HEAD`. So the bar is that the tree holds nothing but what that child is about to write — `git -C <main checkout> status --porcelain`, and EMPTY is the bar, an untracked file included, since `add -A` takes one exactly as it takes a modification. A child that runs PARALLEL cuts worktrees beside that tree, so the bar reads a SECOND place: the WORKTREE ROOT the reference file spells, under which the PLAN mode's §6 cuts `<worktree root>/<slice>`. Nothing in that path names the child that owns the slice, so a worktree left standing there fails the bar whichever child left it, since `git worktree add` creates the branch BEFORE it fails on an occupied path. At arming time the next child's slices may not be cut yet, so nothing here can say which path would collide. The bar is read before the first child, before every child behind a closed or a set-aside one, and before the first child a resumed roadmap arms; a probe that cannot answer at all passes neither of them, because a fact nobody can read may never pass for the reassuring one.

Four things fail it, and the first three are what a set-aside leaves:

- **A child set aside mid-slice** left its applier's uncommitted edits standing, which that mode leaves deliberately. Armed over them, the next child COMMITS them inside its first slice's commit and its verifier judges them inside that slice's diff — a child credited with work it never wrote.
- **A child set aside on a merge conflict** left the checkout conflicted with markers in it, which that mode also leaves deliberately, both halves' branches standing beside it. As the next child's CHANGE BASE no bar can pass that, so its first verification is red for a reason no slice of it explains.
- **A child set aside mid-WAVE** left that wave's worktrees standing under that root, which that mode leaves deliberately too: no worktree is torn down while any slice of the wave is still working, and a wave that never integrates never reaches the integrator whose last act removes them. The porcelain probe reads EMPTY over them, since a worktree dirties nothing in the main checkout — the whole of why the second probe exists.
- **Whatever was already uncommitted when the chain started.** The same `add -A`, the same false attribution, and the chain makes no exception for it: with the operator present a mis-commit is seen and amended, and this mode's whole premise is that nobody is watching the ones it writes.

What this bar does not reach is the BRANCHES those worktrees hold: `oso/<change>/<slice>` names the change that owns it, so however many stand there, the next child's own cut collides with none of them and neither probe needs to read them.

**What the chain does when the bar refuses: it arms NOTHING FURTHER.** Every child still un-run is SET ASIDE — §3's own word, carried no further and never executed — each recorded with the tree or the standing worktree that stopped it and the child that left it. The roadmap is disarmed below, and all of it reaches §5 beside everything §2 queued. It is not a stall in front of the operator: the chain reaches its end and reports instead of waiting for somebody who is not coming, the same trade §3's last bullet makes when it lets a queued decision cost a child rather than the chain.

Nothing the bar stopped on is touched on the way out. Three alternatives were weighed and each is worse. DISCARDING the work is over §2's own irreversibility bar, refused before any tier is consulted. COMMITTING it under the next child's name is precisely the false attribution the bar exists to refuse, and committing it under the set-aside child's name puts work no verifier ever read into the base every later child builds and verifies on. NAMING it and arming anyway is the first of those two with a sentence in front of it. The tree is the operator's: the partial edits are theirs to finish or drop, the conflict theirs to resolve or abort. A standing worktree is theirs the same way and for one reason more. `git worktree remove` refuses one holding uncommitted work, and forcing it is the one removal §2's never-solo list keeps for them. The SessionEnd teardown is no fallback — its own removal is unforced too, so it logs the failure and leaves the tree standing, then drops the state file that named the repository to prune it in. Such a worktree stands INDEFINITELY, and disposing of it is the operator's alone; until they do it is where they read what those slices did.

**What survives the session, and what picks it up.** The chain runs IN-SESSION: it needs no relaunch while the session lives, and a compaction mid-chain costs it its WINDOW and never its POSITION, because everything it knows is written down rather than remembered. The survivability FLOOR is the host's own re-anchor after a compaction, which the reference file names, and what that re-anchor reads is exactly what is written down: the `oso/index` row's `NEXT:` line, `oso-state show`, and the run journal each child's milestones are appended to.

- **Armed before the first child**, and read back the way every state write in these flows is: `oso-state set roadmap={roadmap}` with §1's slug, then `oso-state show`. It arms NO gate — nothing in the harness gates on it, and no gate ever will — so a write that did not land costs recoverability and never safety: record it and run on, rather than stopping the chain over a key nothing denies on.
- **And the unattended marker beside it, armed per CHILD rather than per chain.** Every arming above also writes `oso-state set auto=running auto_change=<that child's slug>` — the marker `_shared/unattended.md` defines, arriving here because a child of this chain is unattended by construction rather than by an operator's flip. The child's own park or close then flips it exactly as that mode states. What it arms on a host is `_shared/unattended.md`'s to say. `auto_change` is what names the run journal beside that — the file every one of that child's milestones is appended to full-text with `oso-state journal`, which is what the operator reads on their return and what §5's own report is assembled from. The disarm below drops it with `auto=done` beside `roadmap=none`. The FIRST arming in this project also reads the per-project `oso/preferences` record for the ceiling fields `_shared/unattended.md` defines — the staging route, the production route and the PR base branch. Where the record lacks them, it asks ONE round through the host's question tool, inside the per-round cap the reference file names, writing both the answers (`mem_update` — merge, never overwrite) and the deny-pattern mirror `_shared/unattended.md` spells before the first child arms. It is asked once per project and never again per child; where nobody is there to answer, `_shared/unattended.md`'s own answer to a missing record governs the child exactly as it governs a plain run.
- **Beside a child's own keys, never over them.** A state write merges, so `mode`, `active_slice` and `verify_green` keep saying exactly what the child's own §5 and §6 make them say, and this chain runs `oso-state clear` at no point between children.
- **Disarmed the moment the chain has nothing left to arm** — every child closed or set aside, the bar above having refused or not — with `oso-state set roadmap=none auto=done`: the sentinel, because `oso-state` can set a key and never delete one, exactly as `active_slice=none` closes a slice. A claim on this repository that outlives its chain is an instruction to resume something nobody is running, and it is the flow's own job to drop it rather than a hook's to guess at it.
- **A session that DIED mid-chain never reached that disarm**, and the harness closes that end without depending on the flow. The SessionEnd teardown drops a state file naming a roadmap in flight for the session that armed it, worktrees first. The SessionStart signal for a state file this repository's own names the roadmap's resume route instead of the change's when the file names one, plus the one command that drops the claim locally. Nothing is auto-resumed: the next session is told, and the operator's re-invocation is what runs. What that re-invocation then does is this section from the top — read the roadmap's ledger topic and its index row, re-arm the key, and arm the first child the record leaves un-run, its tree read against the bar above like any other.

## 5. The presence phase

Everything the chain would have put to the operator is consolidated here and presented once, on their return. This is the flow's one return to them after §3, and it is what lets a decision that needs them cost the chain nothing at the moment it arises: the cost is paid HERE, in one sitting and against one queue, rather than by a run nobody is watching stopping to ask.

**What reaches it, and the list is closed.** Every item names the child it came from and the point in that child where it arose:

- **Every decision §2 queued instead of answering** — one over its irreversibility bar, one on its never-solo list, one no tier could justify on the evidence in front of it, or a RECONCILIATION between an entry a child inherited and that child's own contrary evidence. Each arrives as the question it was, carrying the options and the tradeoffs the silent tier would have put to the operator, never as a summary of the impasse.
- **Every child such a decision SET ASIDE**, as ONE item with the decision that set it aside rather than as a second entry further down — the question and what it cost are read together. §3's two points cost differently and the item says which. A child stopped while being PLANNED froze no ledger, so §3's own exception stands over it — nothing to present and nothing to execute — and the answer is what lets it be planned at all. A child stopped mid-EXECUTION carries the slices it landed, committed, the ones behind them never executed, and whatever its stopped slice or wave left standing in the tree.
- **What stopped the chain**, where §4's bar refused an arming: the dirty checkout or the standing worktree that failed it, the child that left it, and every child the refusal set aside behind it. A standing worktree travels with its PATH whichever way it got here — named by the bar that refused over it, or left by the LAST child, where nothing armed behind it for the bar to be read at all. No later teardown clears it, and until the operator disposes of it, it is where they read what those slices did.
- **Every child's own non-code pendings and named residuals** — the `PENDING:` rows and the residuals its judges left recorded, from the children that CLOSED as much as from the ones set aside. Each child's own close already recorded them; what this phase adds is that they arrive TOGETHER, so the operator reads one queue instead of assembling it out of every child's record.

**Prioritized means ORDERED, and the order is a rule rather than a judgment** — the same run consolidated twice yields the same queue in the same sequence. Rank by what an item's answer releases, most first, and break every tie by §1's run order and then by the point inside that child where the item arose:

1. **What stopped the chain** — every child behind it went un-run.
2. **What set a child aside** — one child stopped, and the slices it never executed wait on this answer.
3. **What cost its child nothing** — a decision queued mid-execution over something that child's progress did not wait on: it closed anyway, so the answer shapes what comes after it and releases nothing.
4. **What awaits their hand** — the pendings and the residuals, where nothing is blocked and the work is simply theirs.

**The final report HEADS the queue**, three parts and no fourth. It ACCOUNTS where the queue ASKS, so nothing is written twice — a deferral is named here and put as its own question below:

- **What was decided for them, and on what rationale** — every decision §2's policy took, as the delegated mark already records one: the decision, the tier that answered it, and why that tier was the one reached. This is what the one approval actually bought, and reading it is how an operator audits a policy they declared before any of it happened.
- **What was deferred, and why** — every item this queue holds, each with the reason no tier took it: over the bar, on the never-solo list, unjustifiable on the evidence in front of the tier, or a reconciliation only they can settle.
- **What awaited their hand** — what no answer of theirs releases: the tree the bar refused, a standing worktree with its path, the un-run remainder of every set-aside child, and the pendings each close left.

**What the operator hears while the chain runs, and what fetches them back.** Every milestone the chain reaches is reported under the contract the ground rules bind it to, into the session stream they read when they return. Three moments are different in kind: at each of them the flow has STOPPED and what happens next is the operator's, so a stop is the whole of what a notification is here — this mode drives no notifier of its own and claims no transport to any device.

- **The roadmap is COMPLETE** — the chain has nothing left to arm and this phase has delivered.
- **The presence queue is READY** — that delivery carries items, and they wait on the operator.
- **The chain is BLOCKED** — it cannot go on and no set-aside disposes of it, because what stopped it was never a decision; a stall nobody is there to clear is the same moment. A verifier that cannot verify at all — a broken environment, a missing command — is the shape of it, and no tier of §2 substitutes for a tool that will not run. Say what stopped and where, then stop there: never loop over it, and never wait in silence for somebody who is not coming. The `roadmap` key stays armed, because §4 disarms a chain with nothing left to arm and this one still has children un-run, which is what lets a resumed session pick the run up where it stood. The child's own marker goes the other way in that same breath — `oso-state set auto=parked`, the value `_shared/unattended.md`'s park defines — for the reason `_shared/unattended.md`'s own park already gives.

The first two land in the same breath whenever the queue is not empty, and that is ONE stop and one report rather than two — the report at the queue's head is where the operator reads which of them they got. A per-child CLOSE is none of the three, and neither is an arming, a verdict read or a judge's outcome: the chain arms the next child in the same breath, so nothing there waits on the operator. A push per close would turn a ten-child roadmap into ten interruptions that each say the same thing.

"In the same breath" is the host's to make true, and it is not free everywhere. Under a host whose delivery contract carves an unattended run out of its turn-ending rule, the close's report and the next child's arming genuinely share the turn. Under one that carves out none, that contract still governs: the report ends the turn and the arming follows in the next one, which costs the chain a turn per child and stops it at none of them. Every one of those still reaches the session stream, and the chain runs on.

Exit: the report and its ordered queue are delivered under the host's delivery contract, every item carrying its child and its point. The roadmap's ledger topic holds that queue as presented (`mem_update` — merge, never overwrite), and the `oso/index` row's `NEXT:` line says the chain has nothing left to arm rather than naming a child, the row keeping `status: roadmap`, which marks a parent and never progress. §4's disarm has run, and that is what ends a roadmap. This phase decides nothing and starts nothing: an answer the operator gives here is recorded where that decision's record already lives — the roadmap's ledger topic, and the child's own ledger where the decision is that child's — and re-invoking the mode is what runs on it, through §4's resume route.
