# OpenCode parity

Certification record for the OpenCode host, filled in by three suites under `core/test/certify/` — `opencode-contract-bar.test.ts`, `opencode-behavior-bar.test.ts` and `opencode-wave-runner-smoke.test.ts` — run under `OSO_CERTIFY=1` against the pinned binary. It records what those suites measured, what they left unmeasured, and how their rows diverge from the bash bars and smoke they port — never a description of intended behavior. Release-level host divergence between Claude Code and OpenCode remains ADR-0097's own obligation, extended by ADR-0151; this file no longer restates it.

## The pin

OpenCode 1.18.22 — `SUPPORTED_OPENCODE_VERSION` in `core/src/install/pins.ts`, the version every suite's own binary probe resolves the pinned binary against.

| `opencode-behavior-bar.test.ts` | 11 | row-for-row port of `tests/opencode-behavior-bar.sh`, no row-count divergence |
| `opencode-wave-runner-smoke.test.ts` | 10 | `waveSmokeOutcome` in `core/test/certify/support/wave-isolation.ts` gives a host-auto-rejected worktree permission its own `host-refused-the-worktree` outcome, read out of the child's own stream the way `bootstrap/verify-opencode.sh` already read it. A session that ran and whose model produced nothing else has no such not-run lane: it resolves to `incomplete`, and the wave-runner isolation row's own assertion turns that into a FAILURE rather than a not-run line, exactly as the bash's `run_wave_smoke` treated it. The port carries that classification forward unchanged rather than adding the lane the refusal case gets — on a host whose free-tier model is rate-limited into producing nothing, that is the difference between a nightly red an operator can act on and one they cannot, recorded here as a standing divergence rather than fixed by this slice |

## Standing security residual carried from the release ledger

Two lexer bypasses at the production-deploy gate are ported record for record rather than closed, per `docs/rewrite/ts-core-roadmap.md`'s C2-D17: a command-string-carrying wrapper (`script -qc '…'`, `ssh host '…'`, `tmux new-session -d '…'`) whose payload lands as one quoted token no basename comparison matches, and an `xargs` replace-string splitting the line at `{`, so `echo --prod | xargs -I{} vercel {}` passes allowed and uncounted where `echo --prod | xargs vercel` is denied. Both holes are pinned as fixtures under `core/test/fixtures/gates/` and asserted in `core/test/gates/parity.test.ts` and `core/test/port/lexer.test.ts` rather than fixed; closing either is a security change and stays the operator's, as C2-D17 already recorded.

## What was and was not driven

The contract bar, the behavior bar and the wave-runner smoke have each been driven against a real, pinned OpenCode binary — the wave-runner smoke for the first time in a CI run, never having been wired into the nightly build before this record. The fourth certify suite under `core/test/certify/`, the Codex authenticated smoke, drives a different host; `docs/parity-codex.md` is where its own never-driven-here fact is recorded.

## What the host offered the prompt-free posture, measured at C0-S3

Three readings taken against the installed binary this machine carries, above the pin named above, while `core/test/certify/opencode-prompt-free-posture.test.ts` was written. Each is a measurement of the host, not a statement of intent. Every one of them was taken with `rg -ob --text` for the byte offsets quoted below and `dd` for the bytes around them; `grep` is not an instrument this record accepts, because the `grep` on the machine that took the first pass is ugrep 7.8.4, which answers `grep -c 'auto-rejecting' <binary>` with no output at all rather than with a `0`, and the second bullet records what reading that empty output as a zero cost.

- **The `permission.ask` plugin hook is documented and never dispatched.** `Plugin.trigger` is a generic `hooks[name]` lookup, so a hook fires only where the host passes its name to it. Every literal `trigger("…")` call site in the binary — 34 of them, the complete set — names one of `tool.execute.before`, `tool.execute.after`, `shell.env`, `file.open`, `tab.new`, `tool.definition`, `command.execute.before`, `chat.message`, `chat.params`, `chat.headers`, `experimental.chat.system.transform`, `experimental.chat.messages.transform`, `experimental.session.compacting`, `experimental.compaction.autocontinue`, `experimental.text.complete` and `experimental.provider.small_model`; `config`, `event` and `dispose` are the three the plugin manager invokes directly. `permission.ask` appears exactly once in the whole binary, at byte 103607477, inside the hook-name list of the host's own embedded plugin-authoring guide, and at no call site: the binary carries 22 occurrences of `permission.ask` and 21 of `permission.asked`, and excluding the event name leaves that single documentation site. C0-D5(b) therefore stands unbuilt by the ruling it already carries: the config rows carry (a) alone, `git commit` and `doom_loop` stay the operator's prompts, and `oso profile show` prints them.
- **`auto-rejecting` is present, and this document's first reading of it was a false measurement.** This bullet once recorded the string as absent from the binary, on the strength of a `grep -c` whose empty output was read as a zero. Measured again with `rg -ob --text`, `auto-rejecting` sits at byte 96276366 and `permission requested` at byte 96276300 — sixty-six bytes apart, inside one string, and in code rather than in documentation: the headless `opencode run` command's own loop over the event bus, captured verbatim.

  ```js
  if(B.type==="permission.asked"){let J=B.properties;if(!T.has(J.sessionID))continue;if(Hj)await N.permission.reply({requestID:J.id,reply:"once"});else z.println(z.Style.TEXT_WARNING_BOLD+"!",z.Style.TEXT_NORMAL+`permission requested: ${J.permission} (${J.patterns.join(", ")}); auto-rejecting`),await N.permission.reply({requestID:J.id,reply:"reject"})}
  ```

  ADR-0156's captured line — `! permission requested: external_directory (…/wt2/*); auto-rejecting` — is that template byte for byte. `Hj` is the run's own permission flag, `j.auto||j.yolo||j["dangerously-skip-permissions"]` at byte 96268129: raised, every prompt is answered `once` and nothing is printed; unraised, every prompt prints the line above and is answered `reject`. `WORKTREE_PERMISSION_AUTO_REJECTED_PATTERN` in `core/test/certify/support/wave-isolation.ts` and the wave-runner smoke's `host-refused-the-worktree` outcome therefore both still match on this host, and ADR-0156 stands.
- **One headless turn reached all three harness paths before the posture rows existed.** Driven through the bash tool on a scratch project, a single turn read an installed skill wrapper, ran `oso-state show` and wrote into a worktree under `~/.local/share/opencode/worktree/`, and the child stream carried no `permission requested` line at all — with `permission.external_directory` absent from the rendered config. The shell tool's own description says why: an external *workdir* needs `external_directory` approval, while "command-argument path warnings are advisory only".
