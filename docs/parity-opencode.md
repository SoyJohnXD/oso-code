# OpenCode parity

Certification record for the OpenCode host, filled in by three suites under `core/test/certify/` — `opencode-contract-bar.test.ts`, `opencode-behavior-bar.test.ts` and `opencode-wave-runner-smoke.test.ts` — run under `OSO_CERTIFY=1` against the pinned binary. It records what those suites measured, what they left unmeasured, and how their rows diverge from the bash bars and smoke they port — never a description of intended behavior. Release-level host divergence between Claude Code and OpenCode remains ADR-0097's own obligation, extended by ADR-0151; this file no longer restates it.

## The pin

OpenCode 1.18.22 — `SUPPORTED_OPENCODE_VERSION` in `core/src/install/pins.ts`, the version every suite's own binary probe resolves the pinned binary against.

The three rows the host-posture close added for the applier's bounded `edit` verdict bring the registered count to 61, counted from the suite's own run against the installed binary, above the pin named below; `CONTRACT_BAR_ROWS_PORTED` stays 58 because it names what the bash ported, and the suite asserts it as a floor |

The port carries that classification forward unchanged rather than adding the lane the refusal case gets — on a host whose free-tier model is rate-limited into producing nothing, that is the difference between a nightly red an operator can act on and one they cannot, recorded here as a standing divergence rather than fixed by this slice |

## Standing security residual carried from the release ledger

Two lexer bypasses at the production-deploy gate are ported record for record rather than closed, per `docs/rewrite/ts-core-roadmap.md`'s C2-D17: a command-string-carrying wrapper (`script -qc '…'`, `ssh host '…'`, `tmux new-session -d '…'`) whose payload lands as one quoted token no basename comparison matches, and an `xargs` replace-string splitting the line at `{`, so `echo --prod | xargs -I{} vercel {}` passes allowed and uncounted where `echo --prod | xargs vercel` is denied. Both holes are pinned as fixtures under `core/test/fixtures/gates/` and asserted in `core/test/gates/parity.test.ts` and `core/test/port/lexer.test.ts` rather than fixed; closing either is a security change and stays the operator's, as C2-D17 already recorded.

## What was and was not driven

The contract bar, the behavior bar and the wave-runner smoke have each been driven against a real, pinned OpenCode binary — the wave-runner smoke for the first time in a CI run, never having been wired into the nightly build before this record. The fourth certify suite under `core/test/certify/`, the Codex authenticated smoke, drives a different host; `docs/parity-codex.md` is where its own never-driven-here fact is recorded.

## What the host offered the prompt-free posture, measured at C0-S3

Three readings taken against the installed binary this machine carries, above the pin named above, while `core/test/certify/opencode-prompt-free-posture.test.ts` was written. Each is a measurement of the host, not a statement of intent. Every one of them was taken with `rg -ob --text` for the byte offsets quoted below and `dd` for the bytes around them; `grep` is not an instrument this record accepts, because the `grep` on the machine that took the first pass is ugrep 7.8.4, which answers `grep -c 'auto-rejecting' <binary>` with no output at all rather than with a `0`, and the second bullet records what reading that empty output as a zero cost.

- **The `permission.ask` plugin hook is documented and never dispatched.** `Plugin.trigger` is a generic `hooks[name]` lookup, so a hook fires only where the host passes its name to it. Every literal `trigger("…")` call site in the binary — 34 of them, the complete set — names one of `tool.execute.before`, `tool.execute.after`, `shell.env`, `file.open`, `tab.new`, `tool.definition`, `command.execute.before`, `chat.message`, `chat.params`, `chat.headers`, `experimental.chat.system.transform`, `experimental.chat.messages.transform`, `experimental.session.compacting`, `experimental.compaction.autocontinue`, `experimental.text.complete` and `experimental.provider.small_model`; `config`, `event` and `dispose` are the three the plugin manager invokes directly. `permission.ask` appears exactly once in the whole binary, at byte 103607477, inside the hook-name list of the host's own embedded plugin-authoring guide, and at no call site: the binary carries 22 occurrences of `permission.ask` and 21 of `permission.asked`, and excluding the event name leaves that single documentation site. C0-D5(b) therefore stands unbuilt by the ruling it already carries: the config rows carry (a) alone, `git commit` and `doom_loop` stay the operator's prompts, and `oso profile show` prints them.
- **`auto-rejecting` is present, and this document's first reading of it was a false measurement.** This bullet once recorded the string as absent from the binary, on the strength of a `grep -c` whose empty output was read as a zero. Measured again with `rg -ob --text`, `auto-rejecting` sits at byte 96276366 and `permission requested` at byte 96276300 — sixty-six bytes apart, inside one string, and in code rather than in documentation: the headless `opencode run` command's own loop over the event bus, captured verbatim.

  ```js
  if(B.type==="permission.asked"){let J=B.properties;if(!T.has(J.sessionID))continue;if(Hj)await N.permission.reply({requestID:J.id,reply:"once"});else z.println(z.Style.TEXT_WARNING_BOLD+"!",z.Style.TEXT_NORMAL+`permission requested: ${J.permission} (${J.patterns.join(", ")}); auto-rejecting`),await N.permission.reply({requestID:J.id,reply:"reject"})}
  ```

  ADR-0156's captured line — `! permission requested: external_directory (…/wt2/*); auto-rejecting` — is that template byte for byte. `Hj` is the run's own permission flag, `j.auto||j.yolo||j["dangerously-skip-permissions"]` at byte 96268129: raised, every prompt is answered `once` and nothing is printed; unraised, every prompt prints the line above and is answered `reject`. `WORKTREE_PERMISSION_AUTO_REJECTED_PATTERN` in `core/test/certify/support/wave-isolation.ts` and the wave-runner smoke's `host-refused-the-worktree` outcome therefore both still match on this host, and ADR-0156 stands.
- **One headless turn reached all three harness paths before the posture rows existed.** Driven through the bash tool on a scratch project, a single turn read an installed skill wrapper, ran `oso-state show` and wrote into a worktree under `~/.local/share/opencode/worktree/`, and the child stream carried no `permission requested` line at all — with `permission.external_directory` absent from the rendered config. The shell tool's own description says why: an external *workdir* needs `external_directory` approval, while "command-argument path warnings are advisory only".

## What the host's permission schema makes of `edit`, measured at C0 on the host posture close

Taken against the installed binary this machine carries, above the pin named above — the same instrument rule as the C0-S3 readings: `rg -ob --text` for every byte offset below, `dd` for the bytes around them, and `opencode debug config` / `opencode debug agent` against a fixture install whose `HOME`, `USERPROFILE`, `TMPDIR` and every `XDG_*` were pinned away from this machine's own.

- **`permission.edit` takes a path-pattern object, exactly as `read` does.** At byte 104369899 the schema reads `$0=D.Literals(["ask","allow","deny"]).annotate({identifier:"PermissionActionConfig"}),p5=D.Record(D.String,$0).annotate({identifier:"PermissionObjectConfig"}),x1=D.Union([$0,p5]).annotate({identifier:"PermissionRuleConfig"}),g5=D.StructWithRest(D.Struct({read:D.optional(x1),edit:D.optional(x1),glob:D.optional(x1),grep:D.optional(x1),list:D.optional(x1),bash:D.optional(x1),task:D.optional(x1),external_directory:D.optional(x1),…}))`. `read`, `edit`, `bash` and `external_directory` are one and the same `PermissionRuleConfig` — a scalar verdict or a `Record<pattern, verdict>`. Driven against a fixture install, `opencode debug config` echoes an agent's `edit` object back unchanged, and a verdict outside the three is refused by name: `Expected PermissionActionConfig, got "sometimes" agent.probe-applier.permission.edit.*`, which is the validator descending into the object rather than rejecting the shape.
- **The host's default permission object names no `edit`, and its base is allow.** At byte 97099175: `a.fromConfig({"*":"allow",doom_loop:"ask",external_directory:{"*":"ask",…},question:"deny",plan_enter:"deny",plan_exit:"deny",read:{"*":"allow","*.env":"ask","*.env.*":"ask","*.env.example":"allow"}})`. An agent that spells no `edit` rule of its own therefore resolves `edit` through `{"*":"allow"}`.
- **The last matching rule wins, and the config's own key order is the resolution order.** At byte 104095324 the flattener is `function rt(t,r){…for(let[o,i]of Object.entries(t??{})){…n.push(...Object.entries(i).map(([c,k])=>({action:o,resource:c,effect:k})))}…}` — object entries become rules in declaration order — and at byte 99511836 the evaluator is `function Po(o,e,...i){return i.flat().findLast((t)=>So.match(o,t.action)&&So.match(e,t.resource))??{action:o,resource:"*",effect:"ask"}}`. `findLast`, not `find`. The matcher behind `So.match` is at byte 104371219: `function JH(_,Y){let $=_.replaceAll("\\","/"),A=Y.replaceAll("\\","/").replace(/[.+^${}()|[\]\\]/g,"\\$&").replace(/\*/g,".*").replace(/\?/g,".");…return new RegExp("^"+A+"$","s").test($)}` — every `*` becomes `.*` and crosses `/`, so `"*"` alone matches any absolute path. One `edit` ruleset covers all three writing tools, measured at their own assert sites rather than inferred: the patch tool at byte 98886701, the edit tool at byte 98891304 and the write tool at byte 99010216 each call `assert({action:"edit"…})`, and those are the complete set of `assert({action:"edit"` sites in the binary.
- **What that costs the render.** A block spelling the broad allow LAST would have the host resolve every path to allow and the denies would never bind. The rendered `oso-applier` block therefore carries `"*": allow` first and its denies after it, and `EDIT_RULES_THE_HOST_RESOLVES_BY_LAST_MATCH` in `core/src/install/opencode-config.ts` is the single ordered constant the render, the reach row and the contract bar all read. Inverting that constant was driven against the real binary while this record was written: `opencode debug agent oso-applier` then resolves `/home/…/.config/opencode/skill/_shared/rubric.md` to `allow`, and the contract bar's own row reads red for it.
- **Half of that control did not bind, and closing it is not a widening.** The security re-run drove the write tool against the rendered agent and measured `.opencode/plugin/x.ts` — the resource shape the host actually derives for an in-project target — resolving to allow: `LocationMutation.resolve` computes containment from the resolved absolute path and then emits a *bare project-relative* resource, while the matcher at byte 104371219 anchors `^…$` and compiles `**/.opencode/**` to `^.*.*/\.opencode/.*.*$`, which requires a literal `/` before `.opencode`. `**/.config/opencode/**` bound only because a config home is always out-of-project and therefore absolute. Before the host-posture close `oso-applier` spelled no `edit` rule at all and resolved every path through the host's own `{"*":"allow"}`, so the project `.opencode` surface was reachable then too: this is not a widening of anything, and never was. What was new was a control documented and certified as effective while half of it did not bind. The ordered constant now carries each denied surface twice, non-prefixed for the project-relative resource and `**/`-prefixed for the absolute one, and `.git/hooks/**` joined them as the class member the review found — in-project, and executed by the host on the harness's own `git commit`.
- **What binds now, measured through the binary rather than through a matcher rewritten in TypeScript.** The contract bar's edit row no longer reads the ruleset and resolves paths itself; it drives `opencode debug agent oso-applier --tool write --params …` in a seeded repository under the fixture's own pinned home and reads the host's answer. Against the pre-change constant that row read red on exactly two of its five probes — `.opencode/plugin/x.ts executed` and `.git/hooks/pre-commit executed` where `refused` was expected — and green on all five after it: `.opencode/plugin/x.ts`, `sub/.opencode/x.ts`, `.git/hooks/pre-commit` and `/home/op/.config/opencode/plugin/p.ts` refused, `src/index.ts` executed. The host's two refusal shapes are distinguished by the phrases it prints — `prevents you from using this specific tool call` for a pattern deny and `is disabled for agent` for a scalar one — and an `ask` verdict is auto-approved under `--tool`, so this drive reads deny against everything else and never claims to have measured a prompt.

- **`.git/config` selects the hooks `.git/hooks/**` was protecting, so the deny moved up to the whole directory.** `core.hooksPath` is what `opencode-install.ts` writes with `git -C <repo> config --local core.hooksPath <target>` to arm the harness's own pre-commit gate, which leaves `.git/hooks/*` inert in every oso-installed repository and the armed gate standing on one line of `.git/config`. Driven through the binary against the ruleset as it stood, on `oso-applier`: `.git/config`, `.git/worktrees/wt/config` and `.git/modules/sub/config` each read `executed` and `.git/hooks/pre-commit` alone `refused`. With `.git/**` and `**/.git/**` in place of the two `hooks` rows, all four read `refused` and `src/index.ts` still `executed`. `.githooks/**` stays writable and reads `executed` before and after, which no longer buys anything: pointing `core.hooksPath` at it is a write into `.git/config`, and that is the row those four probes now close. The applier has no legitimate edit-tool write into `.git` at all — git itself runs through bash, which this block never covers.
- **The grant was config-level while the compensating deny was per-agent, and closing that is not a widening either.** `permission.external_directory` applies to every agent; the edit ruleset renders only into `oso-applier.md`. The primary `build` agent — where every mode command routes, so the orchestrator session itself — has no agent file and resolved `edit` through the host default `{"*":"allow"}`: driven through the binary, a `build` write to `<config home>/skill/_shared/rubric.md` read `executed`. `mergeOpenCodeConfig` now writes a config-level `permission.edit` denying `**/.config/opencode/skill/**` and `**/.local/state/oso-code/**` and nothing else, and the same probe reads `refused` after it while `src/index.ts` still reads `executed`. The two rows are deliberately narrow because a config-level deny binds the operator's own sessions too: denying `.opencode/**` or `.git/**` there would stop the operator editing their own project plugins or hooks through OpenCode, which is their posture and not the harness's, while the applier-level rows already cover those surfaces for every harness child. `<config home>/plugins/engram.ts` still resolves `external_directory` to `ask` on `build` after the change, and reads `allow` only once a grant wider than the harness's own is planted in the installed config — that widening is the row's red.
- **On `oso-applier` the config-level rows are inert, measured rather than assumed.** The host flattens them ahead of the agent's own block, so the resolved edit order reads `**/.config/opencode/skill/**`, `**/.local/state/oso-code/**`, then the render's nine — and the agent's `"*": allow` sits after both, superseding them. Nothing is lost there: the applier's own `.config/opencode/**`, `**/.config/opencode/**` and `**/.local/state/oso-code/**` denies follow that allow and refuse the same two trees.
- **`permission.edit` joins the installer-owned permission containers, with the refusal its three siblings already carry.** `mergeOpenCodeConfig` leaf-merges it the way it merges `skill`, `task` and `external_directory`, so an operator's own rows inside it survive and are counted as preserved, and an operator holding `permission.edit` as a scalar meets the same `holds a non-object "edit"; fix it and re-run` refusal those three have always raised for a scalar. That refusal is loud and names the key; it is recorded here rather than smoothed over.
- **A narrower operator posture is read as information and no longer as damage.** `openCodeConfigStatus` reads a harness grant the operator dropped, dropped whole, put back to a prompt, or replaced by a sub-path as `narrowed by the operator`. Only a grant wider than the harness's own, or an owned row carrying a shape none of `allow`, `ask` and `deny` has, still reads `malformed`.

## What the corrected reach guard reads, and the residual it now prints, measured at C0 on the host posture close

- **The guard read a false negative, and the suite had pinned it as the expected answer.** `grantReachesSurface` compared the trailing path suffixes of a grant's own literal head against a surface name, so `~/.local/share/opencode/worktree/**` read as reaching neither project-relative plugin shape — while the host's matcher at byte 104371219 matches `/home/op/.local/share/opencode/worktree/wtA/.opencode/plugin/evil.ts` against that grant and against `**/.opencode/plugin/**` alike, both `true` when driven. The guard now builds a witness from the grant with its wildcards concreted plus the surface's own tail and evaluates grant and surface on it through `hostPatternMatches`, the one translation of the host's compile that `core/test/certify/support/config-fields.ts` also reads. That single function carries the whole of `JH`, the clause the quote above elides included: re-measured at the same site on the binary this machine now carries, `if(A.endsWith(" .*"))A=A.slice(0,-3)+"( .*)?"` is the host's own rule and not a reader's convenience, which is why the path guard and the tool-id readings can share one compile. What it still does not carry is `JH`'s `replaceAll("\\","/")` on either side, absent from the translation before this pass and left absent by it. Measured against the shipped grants, the reading moves from no reach at all to four pairs: `~/.config/opencode/skill/**` and `~/.local/share/opencode/worktree/**` each cover `**/.opencode/plugin` and `**/.opencode/plugins`. The skill grant's pair is a reading this pass took rather than one the finding predicted, and it is the same shape — a `**` that descends to arbitrary depth admits a `.opencode/plugin` under it. The witness itself was rebuilt once more in the same close: it replaced a whole wildcard-bearing segment with `any` and threw the literal prefix away, so `oso-*` concreted to `any`, failed the grant's own regex, and made every `prefix-*` grant read as reaching nothing — `worktree/oso-*/**`, `~/work-*/**` and `skill/oso-*/**` each read no reach at all and each read both `.opencode` plugin shapes once the substitution became in-place (`**` and `*` to `any`, `?` to `a`). That is the shape the per-child worktree scoping will take, `worktree/<change>-*/**`, so the reading mattered before the fix that will use it; the four pairs above are unchanged by it.
- **The two reach rows are named for what they now assert.** Each was `… reach no auto-executed host surface`, a claim the corrected guard contradicts; each now reads `… reach no auto-executed host surface the edit control leaves open`, and its expected side is `REACHES_THE_EDIT_CONTROL_BOUNDS` — the declared residual — rather than the grant list read back. A grant that reaches a surface the residual does not declare parts the two sides and the row goes red, which is what `~/.config/opencode/**` planted into an installed config does.
- **The harness state root joined the edit control, so no reach the row can print is left unbounded.** `.local/state/oso-code/**` and `**/.local/state/oso-code/**` sit after the broad allow with the other denies. Driven through the binary the way the rows above were: `.local/state/oso-code/wave.state` read `executed` and `/home/op/.local/state/oso-code/wave.state` read `undriven` against the pre-change constant, both `refused` after it. `oso-state` writes that root through bash, which the block never covers, so the control costs the run nothing.
- **The residual this leaves, recorded as the delegate ruled it.** OpenCode wave: the worktree grant spans every worktree until the launch seam scopes it — operators running PARALLEL on OpenCode carry this until C2-S3/C4-D3.
- **What that residual costs the wave-runner smoke, recorded rather than fixed.** With the grant present, the wave-isolation smoke's `host-refused-the-worktree` branch is unreachable, so that assertion now measures payload discipline rather than a host refusal: `waveSmokeOutcome` reaches that outcome only from a child stream carrying `permission requested: external_directory … auto-rejecting`, and the host raises no such prompt for a directory it was granted.

## The operator's own posture on this machine, recorded as theirs

`permission.bash` on this machine reads `{"*": "allow"}`. It is the operator's own key, preserved by every install and never written by the harness — `mergeOpenCodeConfig` owns `permission.skill`, `permission.task`, `permission.external_directory`, `permission.edit` and the five verdicts in `OWNED_PERMISSION_VALUES`, and records every other permission key as preserved. Deleting that key would not close the grant: the host's own default at byte 97099175 opens with `"*":"allow"`, an action-`*` resource-`*` rule that covers `bash` on its own, so bash-allow is the host's default and the operator's key at once and only the first of the two is anybody's to remove here. While that grant stands, `external_directory` is not a containment boundary for bash: the shell tool's own description already says an external *workdir* needs approval while command-argument paths are advisory only, so a bash command may read and write outside any granted directory without raising an `external_directory` prompt at all. This is a statement of fact about the operator's configuration. The harness neither changes it nor judges it, and `oso profile show` prints what remains a prompt.

## What the rendered agent blocks close of the MCP surface, measured at C0

- **oso agents' MCP surface: closed to the harness's three servers; operator-declared servers reachable until a render-time closure lands.** `oso verify --host opencode`'s `owned MCP servers closed on every installed agent` row asserts `context7_*`, `engram_*` and `fallow_*` against every rendered block, and prints every other declared server beside the agent count it stays reachable on rather than failing the operator's own configuration. The gap is mechanical: a deny-list cannot name a server it does not know, and install-time edits collide with the byte-assertion.
