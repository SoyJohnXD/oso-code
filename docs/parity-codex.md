# Codex parity

Release ledger required by ADR-0097. It records what Claude Code and Codex do not share, why, and the assurance left after each adapter's mitigation. The neutral body under `plugin/skills/_shared/bodies/` states a rule that is true on both hosts; the file under `plugin/skills/_shared/platform/<host>/` states how that host spells it. A rule written once and carried without a capability or assurance difference never appears here.

## How to read this file

- **Settled** — both hosts have a verified answer and the relevant platform files carry it.
- **Degraded** — the Codex adapter preserves the workflow with a narrower capability or assurance, stated after its mitigation.
- **No package counterpart** — Codex can provide the behavior only through installer-owned user surfaces, not through the plugin package itself.

An unknown host fact blocks a release claim; this document does not ship placeholders. Release 0.18.0 is verified against the Codex 0.146.0 floor in ADR-0094.

## The divergences

| Block | Claude Code | Codex | Status |
|---|---|---|---|
| Shared-file paths | `${CLAUDE_SKILL_DIR}/../_shared/<file>.md` | `../_shared/<file>.md`, resolved against the directory holding the `SKILL.md` — the rule Codex states for every relative path a skill writes | Settled |
| Question rounds | `AskUserQuestion`, 4 per round (its platform cap) | `request_user_input`, Plan-Mode only, with a schema maximum of 3 questions; the Codex binding holds decision rounds to 3 per round and carries a fourth question into the next round | Settled — different host caps |
| The approval gate | `ExitPlanMode`, whose native UI renders and enforces approval of the plan document | The operator enters native Plan Mode before `$oso-code:plan`; `UserPromptSubmit` rejects the skill invocation otherwise. Codex 0.146 reports `permission_mode=default` even for a Plan collaboration turn, so Oso binds the hook's `transcript_path` and `turn_id` to the exact host-generated `task_started.collaboration_mode_kind` event, falling back to the documented field for future compatibility. The same exact-turn attestation guards `Stop` capture, replanning feedback and the transition to approval. A `Stop` hook accepts the exact marker as the final logical line with zero or one host terminal LF, hashes the unnormalized raw field, binds the repaso-first message to pending state, and persists `presented-<digest>.md` plus `current.md`. Codex's native approval control changes the mode and submits the whole case-sensitive prompt `Implement the plan.`; only a same-session pending digest consumes that common phrase, promoting the immutable snapshot to `approved-<digest>.md` and publishing approved state under the same compare-and-set lock. While pending, the catch-all `PreToolUse` hook denies every new local function-tool call; same-session `CANCEL OSO PLAN` remains the abandonment path. Hosted tools, specialized paths and `write_stdin` for an existing process do not cross that hook, so the harness closes live exec sessions before presentation and routes no execution writes through hosted tools | Degraded — native UI signal composed with exact-turn compatibility attestation and a narrower local enforcement rail |
| The post-approval plan artifact | Claude's existing `ExitPlanMode` flow remains unchanged; this release adds no Oso-owned Claude artifact or hook | Oso keeps immutable approval evidence and a mutable operational `current.md` below its per-machine state root. An explicit in-scope hot slice appends through `oso-state amend-plan`, updates the Engram plan observation and waits behind the active slice or wave. A material change becomes a roadmap entry or returns to native Plan Mode for fresh approval | Settled — deliberate Codex artifact, Claude native behavior unchanged |
| Making a launch wait | `run_in_background: false` on the launch (client v2.1.198+) | Codex wait operation plus a repo/agent-keyed receipt published by the host-side `SubagentStop` hook. The caller knows the unique agent id returned by spawn; the hook session id is metadata, never an identity the model has to discover. The receipt is atomic, attempt-scoped, bounded and consumed once; it proves message completion but carries no verdict. The returned message remains the only source of pass/fail/blocked/done/findings | Settled |
| The delivery rule | The TUI drops assistant text preceding a same-turn tool call, so operator-facing content ends the turn | The adapter claims nothing about same-turn preservation and depends on none: operator-facing content ends the turn, and a tool call starts a later turn | Settled — the conservative policy is host-independent; same-turn preservation is outside the contract |
| Invoking a non-forked skill | The Skill tool, under the `oso-code:<name>` plugin namespace | Installed plugin skills surface under the same `oso-code:<name>` identity; operator modes are `$oso-code:plan`, `$oso-code:quick`, and `$oso-code:debug`. An orchestrator opens and reads an auxiliary skill's installed `SKILL.md`; forked judges are the explicit exception in the next row | Settled |
| A forked judge | `context: fork` in the skill's own frontmatter | Four dedicated custom roles pin `gpt-5.5` at `xhigh`. `oso-doubt-pass` alone is `read-only`, since its body judges a frozen-candidate ledger from intent, surface map and bare decisions and runs no project check; `oso-debt-sweep` and `oso-triage` are `workspace-write`, matching `oso-verifier`, because each body's own contract requires re-running a project check (the zero-warnings bar, the one failing check under attribution) that a read-only sandbox cannot execute — ADR-0109 names the accepted residual, that the "never edits" guarantee moves from the sandbox to an explicit instruction in both role files. `oso-security-reviewer` is the D7 exception, with an outer `danger-full-access` role only to launch the networked authenticated CLI and a nested review constrained back to `workspace-write` as detailed in the native-security row. Every explicit `agent_type` is launched with `fork_turns="none"` under ADR-0105; the caller passes the absolute Codex wrapper path, invocation arguments and every required input so the fresh subagent reads the wrapper plus its neutral and Codex-platform bindings itself. S6's handshake, tracked in its own row, still governs when a result may be consumed | Settled |
| The explorer | The built-in `Explore` agent | Codex 0.146's built-in `explorer` role, inheriting the parent Plan Mode's read-only permission; like every explicit role it starts with `fork_turns="none"`, and it is native rather than an eighth oso-code TOML | Settled |
| The integrator's git authority | The agent's Bash tool reaches the main checkout, linked worktrees and git metadata under the host's existing permission model | Codex `workspace-write` protects `.git`, its resolved gitdir and paths outside the active workspace. The merge-only `oso-integrator` role therefore declares `danger-full-access`; its narrow contract still forbids source edits, conflict resolution, history rewrites, force and push. Applier and verifier remain `workspace-write`. A live parent permission override supersedes a role default, so ADR-0100 requires `bootstrap/verify-codex.sh` to give its disposable outer smoke the same authority; ADR-0102 additionally requires the explicit integrator profile to launch fresh, which ADR-0105 spells `fork_turns="none"` against the installed host. The smoke then requires a completed spawn carrying the fixture coordinates, real merge, worktree removal and branch cleanup. Codex 0.146.0's JSON event omits the selected profile name, so the verifier claims delegated behavior, not direct profile-identity attestation | Settled — broader sandbox, fresh explicit role, narrower contract and bounded observer claim |

Approval and handoff hooks retain the real payload session id where same-session isolation is part of their contract | Settled — fixed Codex agent marker, real hook identity where required |

## Frozen loss and degradation ledger

These six entries are release requirements, not a summary inferred from the divergence table. A mitigation stays beside the boundary it cannot remove.

| Loss or degradation | Codex mitigation | Boundary that remains |
|---|---|---|
| Plan approval composes native UI with a narrower local rail | `Stop` binds the delivered document and persists its artifacts, `UserPromptSubmit` consumes native `Implement the plan.` only for the matching pending digest, and pending `PreToolUse` denies new local tool calls | Hosted tools, specialized paths and `write_stdin` on an existing process do not cross that hook. The flow closes its processes and routes no execution writes through those surfaces, but the hook coverage remains narrower |
| Oso voice is global instruction prose instead of an applied output style | The installer owns one bounded Oso block in `~/.codex/AGENTS.md` | Context compaction may weaken it; Claude Code's applied output style has the stronger host-level placement |
| Security review uses a different native reviewer | The dedicated security subagent runs `codex review` with a security-only instruction and reports its exact covered scope | It is not Anthropic's native `security-review` skill; the review engine and report semantics are Codex's |
| Two agent sessions in one repository share one state file | Repository keying keeps the main checkout and every linked worktree on the same commit and edit gates | Session isolation is deliberately lost; the last writer owns the file's `session` field and teardown |
| The authenticated integrator smoke runs outside CI | `bootstrap/verify-codex.sh` always reaches a `passed:` summary and runs the real delegation when Codex authentication is available | CI sets the explicit `OSO_VERIFY_SKIP_SMOKE` boundary; authenticated release evidence requires an operator-run local release check |
| The oso permission profile is the machine default because Codex has no per-project profile selection (ADR-0122) | The extended secret denylist, `.git/config` = `"read"`, and the metadata-IMDS denies from ADR-0121 apply to every session regardless of relatedness | Any Codex session on this machine, not only oso-code work, can write under `.git` outside `.git/config`, and can reach every repository's `oso-state` flags, plan documents and install-backup snapshots under the shared state root |

## Where the shared tree has to land

The Codex wrappers under `codex/skills/<skill>/SKILL.md` reference `../_shared/…`, which resolves inside the installed plugin's skills root. The installer assembles a private marketplace under `~/.local/share/oso-code/codex-marketplace`, copies `plugin/skills/_shared/` beside the eight wrappers, and registers that self-contained root. The tracked marketplace template is therefore distribution input, never a claim that raw `codex/` alone is complete.

Every release that touches either host tree reviews this ledger under ADR-0097. “No change” is a valid review result; leaving a known loss, a changed host cap or a future-tense verification claim unexamined is not.
