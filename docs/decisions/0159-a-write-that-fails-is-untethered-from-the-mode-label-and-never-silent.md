# 0159 — A write that fails is untethered from the mode label, and never fails in silence

Date: 2026-09-11
Status: accepted
Reconciled: applied — `docs/measure-codex-hook-sandbox.md` records the three probes below against `codex-cli 0.153.2`; `core/src/state/store.ts`'s `remedyForUnwritableStateRoot` and `stateRootWritabilityFault`, `core/src/gates/stale.ts`'s four-way `judgeStale` and `core/src/gates/planrail.ts`'s `StateRootUnwritableError` classification carry the two findings into the runtime
Source: this change (codex-desacople); ledger decisions D2 (the writes are untethered from the read-only window, not the flow from the mode) and D9 (the rail never fails silently in a window Codex itself will not enforce that for); D15 and D16, the two measured facts this decision also carries forward

## Decision

### D2, measured rather than reasoned about: the Stop hook is on the other side of the sandbox from the model

A real Codex run went inert for sixteen delegations after the model's own `oso-state` call returned `EROFS`, and the first diagnosis assumed the read-only sandbox reached the `Stop` hook too. It does not. `docs/measure-codex-hook-sandbox.md`'s Question 1 ran `codex exec --sandbox read-only` against a disposable home with the harness state directory declared as a writable root: the model's own shell command got `EROFS` on that directory in the same run, while the `Stop` hook subprocess wrote into it without error — corroborated independently against a target directory declared nowhere in `writable_roots` at all, where the hook still wrote unconditioned by the declaration. The literal framing of "during a Codex Plan-Mode turn" could not be tested the same way: `collaboration_mode` is not a recognized `-c` key under `--strict-config`, and a natural `codex exec` run always reports `collaboration_mode_kind: "default"` — Plan Mode is reachable only from the interactive TUI, which no bounded probe in this repository drives. The operative variable was always the read-only sandbox window, never the mode label, which is what D2 states and this measurement confirms directly rather than by inference.

### D9, measured: three failure shapes and none of them surface to the operator

The same record's Question 2 drove a Codex `Stop` hook through three conditions. Exit `1` is silently ignored — `codex exec` itself exits 0 and nothing in its JSON stream or stderr names the hook, its code or its text. Exit `2` blocks the `Stop` and feeds the hook's own stderr back to the agent as new input, looping for as long as the hook keeps answering `2` — reproduced independently by `core/test/certify/support/codex-stop-drive.ts`, whose hook answers `2` exactly once and closes the loop on its second, `{}` reply. An uncaught exception with no explicit exit call is silent on its reproducible attempt, indistinguishable from exit `1`. None of the three reach the operator on their own. The invariant D9 names — a rail this repository built never fails silently — is therefore not something the host enforces on this repository's behalf in that window; it is something oso-code's own gate code has to keep enforcing itself, all the way to the process boundary a future change to `runCapturePlan` could otherwise let an exception cross.

### What the runtime now does with both findings

Eight state-writing verbs used to reach the state root through a bare `mkdirSync` and hand the operator a raw Node errno; the ninth already asked first and explained itself. All nine now pass through one guard, `requireWritableStateRoot`, and what changed is what the guard says on failure. `EROFS` names a sandbox mode that forbids writing, where no workspace-root declaration or `--add-dir` helps; `EACCES`/`EPERM` name a directory the operator can still grant; `EEXIST`/`ENOTDIR`, `ENAMETOOLONG`, `ENOSPC`/`EDQUOT` and `ELOOP` each say what is in the way and what moves it; an errno this rail cannot act on says so rather than guessing between two causes it cannot tell apart. `stateRootWritabilityFault` — the probe the session-start gate uses to decide whether to speak at all — no longer creates anything to find out: a root that does not exist is reported as itself, and only a root that already exists is asked, read-only, whether it accepts a write.

`capture-plan`'s own failure needed one more step, because it is the first write of a run and D9 already measured that nothing about Codex's own `Stop` behavior surfaces it: registering `StateRootUnwritableError` with the plan rail's existing failure classifier (`isPlanRailFailure`, `nativePlanFailureCode`) turns an unwritable root into a denial the hook already knows how to carry as its own verdict, so the reason reaches the screen instead of joining the two swallowed shapes D9 measured.

A second, separate silence closed alongside it. Every gate had been reading an unreadable state file and an unarmed repository as the same branch — both allowed, both silent — so a run with no rail at all was indistinguishable from one never armed. `judgeStale`, the one gate every host runs at session start, now tells `unidentified` (no task identity resolves), `unusable` (a state file exists and cannot be read) and `unwritable` (a state root exists and refuses a write) apart, each with its own sentence, spoken once at the start rather than repeated on every call. The gates still allow in every one of these cases — closing them would stop legitimate work over a condition the operator may have every right to be in, the same discipline-rail framing this repository states elsewhere — but the rail can no longer be silent about not being there.

## Consequences

- A run whose state root cannot be written now says so, once, at session start, and again in the exact denial a stalled `capture-plan` needed to reach the operator through Codex's own `Stop` channel — never sixteen silent delegations against a rail that was never armed.
- `core/test/state/state-root-unwritable.test.ts` pins all six distinguishable errno branches plus the undistinguished-cause fallback against the exact remedy text each names; `core/test/gates/degraded-armed-state.test.ts` and `core/test/bin/precommit.test.ts` pin the three-way session-start split against fixture state trees this decision's probe never has to create to answer `absent`.
- D15 (Plan Mode is TUI-only; `codex exec` cannot reach it) and D16 (a Codex `Stop` hook must never rely on a loud throw or a bare exit to be noticed) are the two measured facts `docs/measure-codex-hook-sandbox.md` settles for every later prose reference to either.
