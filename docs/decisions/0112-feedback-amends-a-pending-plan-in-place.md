# 0112 — Feedback amends a pending plan in place, never destroying it

Date: 2026-08-05
Status: accepted
Reconciled: applied — `amend-plan` now takes either an approved or a pending plan; `approve-plan` gained a content-parity check between `current.md` and the presented snapshot; `approve-plan-token.sh`'s ordinary-turn path calls `amend-plan` instead of `cancel-plan` and returns amendment guidance instead of a full re-presentation demand.
Source: the operator's own complaint, captured live in their session — an ordinary Plan Mode reply destroyed the pending document and forced a full re-presentation for one requested change; named directly as the harness answering "cosas muy raras" with blocks and repetition instead of intelligent maneuvering. D18's first half (executable remedies) landed at `d43303a`; this is its second.

## Decision

**A pending plan is amended, never destroyed, by an ordinary Plan Mode reply.** `approve-plan-token.sh`'s ordinary-turn path (`UserPromptSubmit`) used to call `cancel-plan` on any reply that was not one of the two reserved control prompts, wiping the state file, the presented snapshot and the operational copy in one atomic step — the operator's request for one change to one slice cost the complete plan, re-read and re-approved from nothing. It now pipes the decoded prompt to `oso-state amend-plan`, which appends it to `current.md` under a `## Plan Mode feedback` heading and increments `plan_revision`, leaving `plan_approval=pending` standing and the presented snapshot untouched. The returned guidance asks the model to present the amendment — what changed and why — never the complete document again.

**`amend-plan` now takes two amendable states, not one.** Before this decision it required `plan_approval=approved` — the hot-slice route `plan.md:35` still uses, unchanged, to append an in-scope execution slice to an already-approved plan's `current.md` against its immutable `approved-<digest>.md`. Extending it to `plan_approval=pending` reuses the same append-and-increment mechanics against `presented-<digest>.md` instead, with the heading and `Classification` field it writes chosen by which state it found (`Execution amendment` / `in-scope` for approved, `Plan Mode feedback` / `feedback` for pending). Neither branch touches `plan_approval_digest`: the hot-slice branch never needed to, and the pending branch is deliberately answered a different way (below), so the two callers stay correct without a second copy of the verb.

**Approval binds the whole document, not just its digest, so the digest never has to move.** The security property this slice was warned not to weaken: nobody may approve a document they have not read. A naive fix — leave `plan_approval_digest` exactly as `capture-plan` set it, unaltered by an amendment — would let `Implement the plan.` approve the OLD presented text while `current.md` now holds a change the operator has not yet been shown re-presented. `approve-plan` (`plugin/bin/oso-state`) now runs one more check before promoting the presented snapshot: `cmp -s "$plan_current_file" "$plan_presented_file"`. An in-place amendment only ever rewrites `current.md`, never the presented file, so the moment one lands, the two diverge and this comparison fails — `approve-plan` refuses with `the pending plan changed since it was presented; capture it again before approving`, whichever digest is offered, because the digest that would satisfy the compare-and-set was never the point of contention. Only a fresh `capture-plan` — the model re-presenting the updated document with the marker — rewrites both files identically again and restores parity. **Approval still binds the complete, currently-read document; it now does so by content, not only by digest identity**, which is what lets the digest stay put through an amendment without opening a hole.

**`CANCEL OSO PLAN` is untouched.** Explicit abandonment stays exactly what it was: `cancel-plan` under the same compare-and-set lock, wiping the whole pending state. This decision changes only what an ORDINARY reply does; the operator who wants the old destroy behavior still has it; it is simply no longer the default for every reply that isn't a recognized control prompt.

**`plan_approval_session` survives every amendment.** Neither `amend-plan` branch writes it — `publish_state_pairs` only ever removes and rewrites the keys a caller names, so a key no caller names is untouched — which is what ADR-0107 already guarantees for every other state-mutating verb; this decision adds no new caller of that key and needed none.

## Consequences

- An operator asking for one change to a still-pending plan gets an amendment turn, not a full re-presentation: `plan_revision` counts the request, `current.md` records what was asked, and the model answers the delta.
- `Implement the plan.` against a document amended since it was presented fails closed, strictly: `oso-state approve-plan <the presented digest>` refuses even though the digest argument is exactly the one `capture-plan` bound, because the content behind it no longer matches what the operator read.
- The catch-all `PreToolUse` gate keeps denying every local tool for the session with a pending amendment exactly as it already did for an unamended pending — an ordinary reply no longer reopens tool access the way the old cancel-and-restart cycle incidentally did, since there is no cancellation to reopen behind.
- `amend-plan`'s hot-slice caller (`plan.md:35`, post-approval) is unchanged in behavior, inputs and outputs; only its internal validation is now shared with the new pending branch rather than hardcoded to `approved`.
- `plugin/bin/oso-state` and `plugin/hooks/approve-plan-token.sh` are both under the Codex hook trust boundary; their hashes in `bootstrap/hook-hashes.txt` are republished alongside this decision.
