# 0124 — Install backups get a restore, a size-bounded retention sequenced behind it, Impeccable is pinned, and three unbounded operations get the shared bound

Date: 2026-08-06
Status: accepted
Implemented-in: bootstrap/install-codex.sh, bootstrap/restore-codex.sh, bootstrap/lib/install-backup.sh, bootstrap/verify-codex.sh, bootstrap/repair-engram-codex.sh, tests/hooks-test.sh, docs/blueprint.md, README.md
Reconciled: applied — every file above carries the change this decision records.
Source: measured on the operator's own machine: 17 `install-backup-*` snapshots under `~/.local/state/oso-code/`, 1.9 GiB total, the largest single snapshot ~110 MiB; the installed Impeccable skill's `SKILL.md` reads `version: 4.0.2`; `codex plugin marketplace add --help` against the installed `codex-cli 0.146.0`; `git ls-remote --tags` against `pbakaus/impeccable`

## Decision

### Part 1 — a restore that exists, and retention sequenced behind it

**The restore.** `bootstrap/install-codex.sh`'s `begin_transaction`/`rollback_transaction` already back up every target it is about to replace and can restore that backup within a failed run, but nothing let an operator return from a bad installation afterward — a backup nobody can restore from is disk, not insurance. `bootstrap/restore-codex.sh` is the new standalone entry point: `restore-codex.sh [--yes] [--list] [<backup-name>]` lists or restores from any `install-backup-*` snapshot under `~/.local/state/oso-code`, reading the restore targets from that backup's OWN manifest (never guessed from what the CURRENT install-codex.sh writes), so a backup made by an older or newer release still restores. The manifest-replay loop itself moved out of `install-codex.sh`'s `rollback_transaction` into `bootstrap/lib/install-backup.sh` (`restore_backup_manifest`), so the in-run rollback and the standalone restore share one reading of the format instead of two that could drift. One thing the in-run rollback can revert that the standalone restore cannot: `core.hooksPath` is captured only in memory for the run that captured it, never written to the backup itself, so a restore run afterward has nothing on disk to read it back from — named honestly in the script's own usage comment and its post-restore output, rather than silently narrower than the in-run rollback.

**The retention policy, and what it bounds.** The stated problem is 1.9 GiB, not a snapshot count — a single snapshot already runs to ~110 MiB, so "keep the last N" bounds count while leaving size to grow with whatever a future release's transaction happens to back up. `prune_install_backups` in `install-codex.sh` therefore bounds total disk size: 300 MiB (`INSTALL_BACKUP_BUDGET_KIB`, overridable via `OSO_INSTALL_BACKUP_BUDGET_KIB`), keeping as many of the newest snapshots as fit — roughly 2-3 at the measured ~110 MiB size, a real fallback depth rather than just the last one — while cutting the measured worst case by over 80%. The newest snapshot is always kept regardless of budget, so the run that just installed is never the one a tight budget empties.

**The sequencing.** A retention policy that runs on its own first installation would delete the very artifacts an operator would reach for if that installation goes wrong — the assignment's own rule closes this: the purge runs only after the restore path has been exercised at least once. `prune_install_backups` refuses to delete anything until `~/.local/state/oso-code/.install-restore-verified` exists, and the only thing that ever writes that marker is `restore-codex.sh`, after it has actually restored a snapshot. On a machine that has never run a restore, retention is a standing no-op that names why it did nothing — backups accumulate exactly as they do today — and pruning turns on only once the restore path has been proven to work, never before. `prune_install_backups` runs after `TX_COMMITTED=true`, outside the transaction: a prune failure is disk pressure, never a reason to roll back an install that already succeeded — its call site carries the same `|| true` `on_exit` gives `rollback_transaction`, so a permission error deleting an old snapshot cannot turn an install that already succeeded into a nonzero exit or a missing success line.

### Part 2 — Impeccable pinned to the tag the recorded read names

`install-codex.sh`'s `mount_impeccable`/`find_impeccable_source` acquired Impeccable from `pbakaus/impeccable` with no commit, version, or digest pin, so two installations a week apart could mount different content with nothing noticing. `codex plugin marketplace add --help` (installed `codex-cli 0.146.0`) documents `owner/repo[@ref]` and a `--ref <REF>` flag as a Git ref for Git marketplace sources — the mechanism this pins ON. `git ls-remote --tags` against `pbakaus/impeccable` shows the upstream repo tags every skill release `skill-v<semver>` (`skill-v3.0.4` through `skill-v4.0.4` at the time of this decision), on a release line independent of its `cli-v*`/`ext-v*` tags — confirming ADR-0059's own finding that the plugin and the npm CLI share no numbering.

Slice B8 (426ba25, ADR-0116) made the design-foundation slice read the installed skill's `SKILL.md` frontmatter and record the `version:` field it carries in the plan ledger, precisely so a pin would have something to reconcile against — the version on the machine that motivated both B8 and this slice reads `4.0.2`. `SUPPORTED_IMPECCABLE_VERSION=4.0.2` in `install-codex.sh` is the single pin both sides now read: `fetch_pinned_impeccable_source` fetches `codex plugin marketplace add pbakaus/impeccable --ref skill-v$SUPPORTED_IMPECCABLE_VERSION`, and `mount_impeccable` verifies — both a discovered candidate before it fetches anything, and the mounted skill after `mount-impeccable.sh` runs, as defense against a mistagged or moved upstream tag — that `impeccable_skill_version` (the same `version:` frontmatter field ADR-0116's read names, and the same field `mount-impeccable.sh` already validates the shape of) equals the pin, failing loudly and by name otherwise rather than mounting unpinned content. A discovered source (a test override, or an already-installed marketplace checkout) that does not already agree with the pin is never trusted as-is; it falls through to the pinned fetch instead.

### Part 3 — the three unbounded operations

`codex login status`, the `codex exec` integrator smoke (slice B13, 9533b38), and the repair downloads in `bootstrap/repair-engram-codex.sh` all ran unbounded — a hang in any of them is the harshest form of the blocking this whole change exists to reduce. Two get the in-shell bounded-subshell idiom `plugin/skills/_shared/front-surface.md` defines and slice B11 already reused for the MCP drift check (`bootstrap/verify-codex.sh`'s `mcp_server_tool_names`): `bounded_command_output` in `verify-codex.sh` is the same job-control-plus-poll-loop technique, generalized to any command instead of the drift check's own JSON-RPC-specific variant, and both `codex login status` (`CODEX_LOGIN_STATUS_BOUND_SECONDS`, default 20s — the same "is this reachable at all" bound the pin recipe uses) and the `codex exec` smoke (`CODEX_EXEC_SMOKE_BOUND_SECONDS`, default 180s — a real end-to-end delegation, not a fast probe) now run through it. A fired bound prints `SLOW: <operation> did not answer within <n>s` and returns 124 (`timeout(1)`'s own reserved code), naming the operation by name rather than a silent skip or a false failure folded into the command's own error.

The repair downloads are different: curl and wget each already ship their own portable connect/transfer timeout flags (`--connect-timeout`/`--max-time` for curl, `--timeout` for wget), so no job-control workaround is needed there — writing one anyway would be the third bounding technique the assignment says not to write. `download_file` in `repair-engram-codex.sh` passes `ENGRAM_DOWNLOAD_BOUND_SECONDS` (default 120s) to whichever tool is present and reports by name and by cause: curl's exit 28 (its own reserved code for a fired `--connect-timeout`/`--max-time`) is named `SLOW: download of <label> did not finish within <n>s`; any other nonzero exit from either tool is named `UNAVAILABLE: download of <label> failed`.

## Consequences

- `bootstrap/restore-codex.sh` is a new, independently invocable script; nothing under `bootstrap/install-codex.sh`'s own flow calls it, and nothing under it runs automatically — an operator chooses when to restore.
- `prune_install_backups` is a standing no-op on every machine that has never run `restore-codex.sh`, including every existing `install-codex.sh` test fixture; retention only engages after a real restore has been proven, and the newest snapshot is never pruned by any budget.
- `install-codex.sh`'s in-run `rollback_transaction` now delegates its manifest replay to `bootstrap/lib/install-backup.sh`'s `restore_backup_manifest`, shared with `restore-codex.sh`; its observable behavior — including the `rollback complete`/`rollback incomplete` wording the existing partial-rollback-honesty tests assert on — is unchanged.
- `mount_impeccable` now fetches a pinned Git ref (`skill-v4.0.2`) instead of the bare, unpinned `pbakaus/impeccable`, and fails loudly if the mounted skill's own frontmatter ever disagrees with that pin — a version bump is a deliberate edit to `SUPPORTED_IMPECCABLE_VERSION`, reconciled against a fresh design-foundation-slice read (ADR-0116), never a silent drift.
- `codex login status`, the `codex exec` smoke, and the Engram repair downloads each report a firing bound by the operation's own name; none of the three can hang this harness indefinitely.
- CI's pinned `verify-codex.sh` failure count (14) is unchanged: `bounded_command_output` and its two call sites run only inside `run_authenticated_smoke`, past the `OSO_VERIFY_SKIP_SMOKE` return CI's fixture always takes before reaching either changed line.
