## Decision

Runtime state stays where ADR-0003 put it — flat `key=value` lines under `~/.local/state/oso-code/`, one file, outside every project — and stops being named after the session.

**The identity is the repository**, spelled `git rev-parse --path-format=absolute --git-common-dir` and digested into a file name. The absolute spelling is the whole decision: the bare form answers a relative `.git` in the main checkout and an absolute path inside a linked worktree, which is one repository under two names, and ADR-0094 records the run that proved both. Where git places nothing the directory the work happens in is the identity: outside a repository there is no commit for the rail to gate, and one directory still answers one name.

**The name is a digest of that path, not the path sanitized.** No sanitizer keeps two repositories apart, because a file name has a charset and a length a path has not. `sanitize_session` drops every byte outside `[a-zA-Z0-9-]`, which maps `/home/a/b` and `/homeab` onto one name; translating each of those bytes to a dash instead maps `my_app`, `my-app`, `my app` and `my.app` onto one name, because a dash is itself inside the charset and every distinguishing byte that is dashable is erased. Length opens the same gate by the other door: a repository nested past `NAME_MAX` has no name to write at all, so its red state is never stored and the gate reads nothing, which is an allow. Both are the failure this whole rail exists to prevent — a red repository whose commit gate opens, on a neighbour's `verify_green=true` in the first case and on an absence in the second. So the name is the SHA-256 of the absolute identity: fixed-length, hex, and needing no sanitizing against traversal. GNU coreutils spells it `sha256sum` and macOS `shasum -a 256`, the pair `seconds_since_modified` already sets the precedent for; a host that answers neither can key no state, so the gate blocks rather than filing every repository under one name.

**A gate arms only on an agent marker, and the marker is not the same channel in both gates**:

- The git `pre-commit` hook reads it from its ENVIRONMENT: `CLAUDE_CODE_SESSION_ID`, which the client puts in every process its Bash tool starts, or `OSO_AGENT` on a host that publishes no session id of its own. This is the only gate a human can meet, because `core.hooksPath` points at it for every commit in the repo, and under repository keying the state file exists whether or not an agent is running — so the marker is now the whole of what keeps the gate off the operator's own commits.
- The two `PreToolUse` gates read it from their PAYLOAD, unchanged. They have no environment to read: the client injects no `CLAUDE_CODE_*` variable into a hook process. The audit trail proves it rather than assuming it — every line this repo's own log carries from a `PreToolUse` gate (854 `residue-allowed`, 13 `commit-denied`, 9 `edit-denied`) has an empty `client` field, which `log_event` fills from `CLAUDE_CODE_EXECPATH`, while every line written by `oso-state` or by the git hook under the Bash tool carries `2.1.220`. A gate armed on that absent variable would be a gate that never fires again on either tool.

**Worktree paths and the audit trail stay session-scoped.** `~/.local/state/oso-code/worktrees/<sanitized session>/<slice>` and the `session` field of `events.jsonl` are not what this decision rekeys: a worktree belongs to the run that cut it, and an audit line to the session that caused it.

**The state file records the session that armed it.** `oso-state set` writes `session=<id>` beside the caller's keys. SessionEnd runs in no working directory — that is why ADR-0088 put `repo_path` in the file — so it can no more compute the repository's name than it can the repo path itself; the sweep it already walks for orphans is how it finds the file, and the recorded session is what tells it which one is its own.

## Consequences

- **The gates reach one repository from every tree of it.** A wave's applier commits in a linked worktree and the `pre-commit` hook there reads the state the orchestrator armed in the main checkout, because both resolve to the same file. Before, that worked only because `core.hooksPath` leaked the session in; now it is the design.
- **State outlives the session that wrote it.** A session that ends cleanly still drops its own file; one that is killed leaves it, and the next session in that repository is armed by what it left. That direction is deliberate: the flags it inherits deny edits between slices and deny commits until green, so an inherited state is more gated than none, never less. `warn-stale-state.sh` names the file at the next start, and the 7-day sweep is what removes it if nobody does.
- **Two sessions in one repository share one file**, and the last write names the session. The one that did not write it finds nothing of its own at SessionEnd and leaves both the state and its worktrees standing — the fail-open direction the teardown already takes wherever it cannot name a repo, and the same worktrees `/plan` §7 clears at the close.
- **A state file from before this change is never read again.** Its name is a session id nothing computes any more, so it arms no gate and answers no read; SessionStart names it once and the 7-day sweep removes it. It carries no `session=` key, so the sweep tears down no worktrees for it — those, if any, are `/plan` §7's or the operator's.
- **A state file no longer names its repository to the eye.** The digest that keeps two repositories apart is what `warn-stale-state.sh` reports and `oso-state show` prints, so the repository behind a file is read from the file — `repo_path` where a wave wrote one, `session` always — rather than off its name.
- **The teardown stops shelling out to `oso-state`.** Reading `repo_path` out of a file it found by sweeping needs no binary, so the `oso-state-unreachable` event ADR-0089 lists has no failure left to record: the reader is `state_value` in `plugin/hooks/lib.sh`, which `oso-state get` uses too, and a hooks directory that exists always ships the library beside it.
