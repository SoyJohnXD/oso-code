# 0158 — The oso permission profile drops its secret denylist, and the change travels to a machine already seeded

Date: 2026-09-11
Status: accepted
Supersedes: ADR-0121's "The secret denylist: extended by principle, not enumeration a second time" section and the `glob_scan_max_depth` widening that existed only to reach it — both are gone from the rendered profile entirely. ADR-0121's `.git` narrowing (`.git/**` = `"write"` with `.git/config` = `"read"` inside it) and its two cloud-metadata network denies are unaffected and still stand exactly as decided there; ADR-0122's return to the machine-default `default_permissions = "oso"` is likewise unaffected
Reconciled: applied — `renderOsoPermissionProfile` (`core/src/install/codex-config.ts`) renders the narrowed table below on every fresh install, and `node bootstrap/oso.js migrate --host codex --yes` (`core/src/install/codex-migrate.ts`) carries it to a machine an earlier install already seeded, since a first-only seed by design never rewrites what it already wrote
Source: this change (codex-desacople); the operator's own reversal, on their own files, of the read-side denials ADR-0121 added there

## Decision

### What the profile denies now

The rendered `[permissions.oso]` table keeps exactly what the discipline rail cannot exist without: `extends = ":workspace"`, the harness state root and its worktree root declared writable under `[permissions.oso.workspace_roots]`, `".git/**" = "write"` narrowed by `".git/config" = "read"` inside it, network enabled, and the two cloud-metadata denies (`169.254.169.254`, `metadata.google.internal`). Nothing else is denied. The three named categories ADR-0121 added — per-tier env files, private-key formats and basenames, whole credential-store directories, twenty-three globs in total — are gone, and `glob_scan_max_depth` no longer moves from its native default of `4`, since that widening to `6` existed only to reach the deeper credential-store patterns the now-removed globs named. The inert `"*" = "allow"` network-domain line is also gone: the domain policy is already permissive once the network switch is on, so the line asserted nothing a reader could not already infer, and its removal was probed both directions against the native profile and changes nothing for the two rules that remain, both fixed-prefix.

Deciding what an operator may read on their own files, on their own machine, was never a call this harness's own install script should make for them. The three categories were a correct answer to "how do we keep this rail from ever reading a secret it stumbles across" when the rail's own writable roots and `"*"` network reach were the threat being weighed; narrowed against the smaller set of things the rail actually needs — the two writable roots above and `.git` — a blanket deny over the operator's own `.ssh`, `.aws`, `id_rsa` and every per-tier `.env` file is a broader claim over the operator's machine than the rail's own footprint justifies. What stays — the `.git/config` narrowing and the two cloud-metadata denies — are both closing a route this harness's own writable roots or network reach could otherwise open; neither reaches outside what the rail itself does.

### The change travels by an explicit command, not by a later install

An install seeds the `oso` profile only where nothing already declares one, and the installer's own printed promise — `Codex permissions are seeded once outside the managed region, and no later install rewrites that choice` — means a machine already carrying the profile ADR-0121 wrote is left untouched by every install that follows this one. `oso migrate --host codex` is the one-time, explicit route the change travels by instead: it rewrites the profile only where it can prove the bytes on disk are the installer's own, by comparing the parsed `default_permissions` root key and the `[permissions.oso]` table against the two exact shapes the installer has ever rendered — the ADR-0121 shape and today's narrower one. Five outcomes, each answered and none of them guessed at: an already-current profile is a no-op (`already-migrated`); the ADR-0121 shape rewrites (`migrated`); no oso-code profile at all declines (`no-profile`); a profile edited by the operator, or under any other name, declines as the operator's own (`operator-edited`); and a config the parser cannot read declines rather than being guessed at (`unparseable`). The root key and its table move together or not at all — a config declaring `default_permissions = "oso"` with no `[permissions.oso]` table beneath it is one Codex itself refuses to start under — and every replaced byte is backed up under the same transactional backup and rollback the rest of the installer uses.

### The CRLF migration's cosmetic cost is two artifacts, not one

A profile migrated from a CRLF `config.toml` gains two extra blank-line artifacts at the boundary between the operator's own content and the rewritten profile, not the one this was first disclosed as. `withoutTrailingBlankLines` (`core/src/install/codex.ts`) strips a block's own trailing blank lines through `FIELDLESS_LINE = /^[ \t]*$/` against lines produced by splitting on `"\n"` alone; a CRLF document's trailing blank line survives that split as a lone `"\r"`, which is not all spaces or tabs and so is never recognized as blank — one CRLF-terminated blank line is therefore left standing, untrimmed. `blocksJoined` then joins the surviving blocks with its own bare `"\n"` separator regardless of the document's own line ending, adding a second, bare-LF blank line on top of the first. Both are confirmed harmless — a blank line inside TOML is inert regardless of which line ending terminates it — and confirmed idempotent: re-running the migration against its own CRLF output reads `already-migrated`, so the two artifacts do not compound on a second pass. Correcting the count here rather than the code is deliberate: nothing about either artifact is wrong enough to justify touching a rewrite path this decision already backs up and rolls back around, for a cost that is cosmetic and bounded.

## Consequences

- A first install on a fresh machine writes the narrower profile directly; nothing about the emptied shape reaches an already-seeded machine until `oso migrate --host codex --yes` runs there once.
- `docs/certify-codex-native-cycle.md` records a run against the profile this decision retires — the run predates this decision's own change by hours — and is annotated there as historical rather than corrected, since nothing in its own prose names the removed content.
- `docs/blueprint.md`'s decision index moves from 157 files to 161 with the three sibling ADRs this change also adds.
