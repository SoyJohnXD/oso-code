# 0153 — The OpenCode installer, verifier and CI host facts

Date: 2026-08-19
Status: accepted
Reconciled: applied — slices S13–S15 of the opencode-parity plan (`docs/opencode-parity-plan.md`) are what arm this ADR: `bootstrap/install-opencode.sh`, `bootstrap/verify-opencode.sh` and the new ubuntu CI step are built and green, and `docs/parity-opencode.md` records the host facts this decision settles.
Source: slices S13–S15 of the opencode-parity plan; the installer's own fixture runs (each category asserted at the path OpenCode actually reads), the S14 clean-room run of `bootstrap/verify-opencode.sh` measured on 2026-08-19 (`passed: 12, failed: 0`, wave-runner smoke over two real worktree children on `opencode/deepseek-v4-flash-free`), and the S15 mutation simulation of the CI step

## Decision

**The OpenCode host's distribution facts are settled: the installer owns the strict-JSON config wholesale and re-applies the operator's five keys, the verifier is self-contained and proves per-worktree isolation with a real wave smoke, and CI pins both halves of the verifier's report. The frozen plan's D6, D11, D15, D20, D21 and D25 land as decided, and the plan's own stale references are corrected here.**

### Part 1 — the installer

`bootstrap/install-opencode.sh` is the single entry point that renders the OpenCode host, mirroring `install-codex.sh`'s transactional shape: `initialize_paths`/`parse_args`/`preflight_*`, a `begin_transaction` over `lib/install-backup.sh`, `rollback_transaction`, `on_exit` checkpoints and `--yes`/`--no-impeccable` flags. What it owns and how:

- **The config is owned wholesale.** `opencode.json` is rendered from a strict-JSON template with no marker region, because this host rejects unknown top-level keys and object-typed `plugin` entries at startup (ADR-0151 part 2). The installer owns the whole file and re-applies the operator's `provider`, `model`, `small_model`, `permission` and `mcp` from the verified backup snapshot. `permission` merges PER SUB-KEY: the installer owns `skill` (the three operator-only denies), `task`, `question`, `plan_enter` and `plan_exit`, while the operator's own `bash` and `read` rules come back whole. The `plugin` key is always an ARRAY. MCP server env is declared under `environment`, never `env`, and a contract check rejects the `env` spelling. D6's two drops are deliberate: `theme` and `agent` are not among the five re-applied keys, and the `oso-*` agents are files under `agent/`, not config, so the harness surface depends on neither.
- **The skill tree lands at the D11 spelling.** Eight wrappers install to `~/.config/opencode/skill/` (singular) with `plugin/skills/_shared/` copied beside them; `permission.skill` deny hides the three operator-only modes from the model while their slash commands stay (ADR-0152). Agents install to `agent/` (singular) and the three commands to `command/`, with the plan command routing to `agent: oso-plan`.
- **The plugin layout is the single discovered entry.** `plugin/oso-code.ts` plus its sibling `plugin/oso/*.ts` modules (no `.test.ts`) and `hooks/routes.ts` beside them — the one-asterisk discovery glob `{plugin,plugins}/*.{ts,js}` means the entry is the only plugin module and the `oso/*` siblings must live outside any plugins directory (D20, ADR-0151 part 2).
- **The global voice block** `bootstrap/opencode-global.md` installs as `~/.config/opencode/AGENTS.md` (D21).
- **Impeccable is acquired pinned, without Codex** (D15): `git clone --depth 1 --branch skill-v$SUPPORTED_IMPECCABLE_VERSION` (the pin read from `install-codex.sh`, 4.0.2), then `lib/mount-impeccable.sh` verifies the mounted skill's `version:` field against that pin; `--no-impeccable` is a recorded opt-out.
- **Engram is wired by its own installer** (D25): `engram setup opencode` when its `--help` announces support; otherwise, and on failure, the operator's prior `plugins/engram.ts` is restored from the backup snapshot as a file.
- **Ownership and rollback are transactional.** An owner registry under `~/.local/state/oso-code/opencode-install-registry` records `installer` vs `operator` per target and key; every replaced target is snapshotted by `begin_transaction` through `lib/install-backup.sh` and restored by `rollback_transaction` on failure. The three project-level `opencode.json` files a repo root owns are never touched — asserted in the fixture.

### Part 2 — the verifier

`bootstrap/verify-opencode.sh` is self-contained and always reaches its summary. Its local checks run against a disposable fixture HOME with PATH shims for `opencode`, `engram` and `fallow-mcp`: the installed version equals the pin, the config contract holds (plugin array, no `env`, the three `permission.skill` denies), the eight wrappers and `_shared/` are byte-exact, the agents are byte-exact, the three commands route correctly, the plugin entry and its siblings (no `.test.ts`) are byte-exact, `plugins/engram.ts` is present, `AGENTS.md` equals `opencode-global.md`, and the owner registry records the installer targets. The TypeScript bar (`tsc --noEmit` + `node --test`) and `bash -n` over the three scripts ride along. The wave-runner smoke (D16) is REAL: a scratch repo with two worktrees created the way the S11 adapter creates them, two children run headless with `--format json` on `opencode/deepseek-v4-flash-free`, each writes a proof file in its OWN worktree and closes with an in-band `status:done`/`verdict:pass`, and the asserts prove per-worktree isolation — each worktree holds only its proof, the root holds none. Every unbounded operation is bounded (120s preflight, 300s children), and there are explicit skip lanes: no model on PATH, no binary, or `OSO_VERIFY_SKIP_SMOKE=1`. The operator's real config is never opened; the fixture HOME is removed by a guarded trap EXIT.

### Part 3 — CI

The new ubuntu step, "OpenCode verify report reaches its summary", pins BOTH halves of the verifier's report — `passed: 12` AND `failed: 0`, measured in a clean-room checkout on 2026-08-19 — because a bare `failed: 0` cannot detect a check removed or added. It runs `cd opencode && npm ci` first, since `node_modules` is gitignored and the TypeScript bar fails without deps, then `HOME=$(mktemp -d) bash bootstrap/verify-opencode.sh` with `OSO_VERIFY_SKIP_SMOKE=1`. The step's comment documents why the verifier is self-contained (fixture HOME + shims), and why the version probe and the smoke skip without a binary or a model. The existing `bash -n` lists already glob `bootstrap/*.sh`, so the OpenCode installer, verifier and purge are covered without duplication; `tests/hooks-test.sh` gains a host-exclusive "OpenCode verifier" block guarded on Windows, asserting a clean run over a fixture HOME with `node_modules` absent and `OSO_VERIFY_SKIP_SMOKE=1`, both skip lanes, and a deliberate wrapper removal turning the run red by name.

### Part 4 — reconciliations with the frozen plan

Three stale or silent references in the frozen plan are corrected here. The pending-divergence row for version agreement cited "S6, S22"; the port has sixteen slices, not twenty-two, and the bar S6 established (`tsc --noEmit` + `node --test` under `opencode/`) is the answer the row carries, so the stale "S22" is dropped. D6's rendered config drops `theme` and `agent` from the installed config — they are not among the five re-applied operator keys, and the `oso-*` agents are files rather than config — which the S13 fixture asserted rather than leaving silent. And the headless `--command` limitation ADR-0152 recorded means the wave-runner smoke runs `opencode run` WITHOUT `--command`, which is the shape the plan already required and this ADR records as settled.

## Consequences

- The distribution facts here are the ones `docs/parity-opencode.md`'s installer, verifier and CI rows record; a later change to any of them is a new decision, never a silent edit to this one.
- The `environment` MCP spelling, the single-entry plugin layout and the `permission.skill` denies are all enforced by the verifier's config-contract check, so a drift in the installer is caught by the verifier and, through it, by CI.
- The operator's five config keys survive reinstall by construction; anything outside them is the installer's to own, matching the transaction discipline the Codex installer already established (ADR-0124).
- CI's `passed: 12` pin is a measured clean-room number, not a floor: it moves only when the verifier's check set moves, and the pin is asserted on purpose so that both directions of drift are visible.
