## Decision

**A fourth operator-only mode, `roadmap`, runs an ordered QUEUE of plan-mode changes: the operator settles the decisions that shape all of them once, approves once, and the flow then plans, executes and closes each child and arms the next.** The queue, the global ledger and the autonomy policy are the operator's exchange; everything after the approval runs on what that exchange recorded.

The mode is a wrapper pair over one neutral body, the shape ADR-0096 requires of every mode here, and it adds no agent role of its own: a child is a plan-mode change, so the appliers, verifiers, integrators and judges it launches are that mode's, launched by that mode's own text.

### Part 1 — one approval, and what it does not buy

ONE approval covers the planning behind the queue and the execution of every child in it. An approval that covered only the planning would put the operator back at every child's gate, which is the pain this mode exists to remove; an approval described as covering "the roadmap" without saying what it excludes is the shape a flow talks itself past later. So the bounds are enumerated where the approval is given, and there are three:

- **A child, or an intent, the document does not carry.** A queue that changes materially after presentation — a child added, an intent redrawn, a global entry reopened — invalidates the approval: the whole document is re-presented and the gate passed again — the rule `bodies/plan.md` §5 already states about its own plan, borrowed rather than restated in a second shape.
- **A child's own plan document.** Every child planned here still builds and delivers the Repaso-headed document ADR-0031 requires, because that document is what the operator reads to see what this approval actually bought. The approval covers that document's approval where the host asks for none; it never replaces the document.
- **A decision the autonomy policy cannot resolve** (ADR-0136). An approval already given is no licence to answer one, and nothing between the gate and the presence phase fetches the operator to answer it either — what it costs instead is ADR-0137's.

### Part 2 — plan-mode children only, and the omission is recorded

**A child is a PLAN-mode change and nothing else is queued.** A roadmap is a sequence of substantial changes decided together, never a list of small fixes with a queue drawn around it, and an ask that belongs in the quick or debug mode meets here the answer Mode 1's own phase 1 gives it: say so, offer that mode, and let the operator decide — never carry it into the queue to be discovered when the chain reaches it.

Quick and debug children are a RECORDED YAGNI rather than a silent omission, and this is where the record sits. Each would need its own answer to questions this version settles for plan alone: what a quick child's approval covers when quick has no plan document to approve, and what a debug child does when no reproduction can be got without the operator. Neither question has a caller yet — the queues that produced this mode were batches of substantial work — and inventing the answers ahead of one would put two more approval shapes into the gate this decision is trying to keep at one.

### Part 3 — both hosts, and the Codex loss recorded rather than implied away

The mode ships on both hosts. Claude Code runs the whole chain on the one approval: `ExitPlanMode` is the gate, phases 1 through 3 are the read-only exchange that builds its document, and nothing between that gate and the presence phase returns to the operator.

**Where a CHILD's own planning runs on Claude Code, then, is outside native Plan Mode, and that is what the single approval costs.** That gate is the transition out of Plan Mode as much as it is the approval, and the way back out of the mode is another `ExitPlanMode` — a second approval, the one thing this approval was given in place of. So a child enters it nowhere: the phases `bodies/plan.md` spells run with the host outside Plan Mode, and the Repaso-headed document its §5 builds is delivered as plain text under the host's delivery contract rather than as that gate's `plan` argument, which is exactly the case Part 1's second bound describes — the approval covers a child's document where the host asks for none. Read-only there is the PLAN flow's own rule, nothing before its §6 writing code, rather than the host's: the edit gate in `plugin/hooks/block-edits-without-slice.sh` denies a file edit only where the runtime state already says `mode=plan` with no slice armed, and a child's planning writes that state only at §5's approval, so the gate stands armed for a child behind one that closed or was set aside and not for the first child of a fresh roadmap. Codex diverges here for the reason the paragraph below gives: its operator re-enters native Plan Mode per child, so a child's phases DO run inside it there. Both halves are recorded in `docs/parity-codex.md` — the Claude fact in the approval-gate row, the Codex cost in the frozen loss ledger.

Codex ships it ASSISTED, and that is a degradation rather than a local variant. Its plan-approval rail passes only on the byte-exact native `Implement the plan.` prompt (ADR-0101, ADR-0103), which no model may produce on the operator's behalf — a harness that types its own approval has approved nothing — so every child stops there. What this host still gives is everything either side of that stop: one planning exchange, one global ledger, the policy answering what surfaces mid-child, the queue advancing without the operator arranging it, and the presence phase at the end. What it does not give is walking away. It goes in `docs/parity-codex.md`'s frozen loss ledger under ADR-0097, with the mitigation beside the boundary it cannot remove, rather than in a footnote.

One further Codex fact is stated in the wrapper rather than assumed: the mode refuses to start outside native Plan Mode, because `request_user_input` — the tool phase 1 asks its questions with — exists only there on that host, and NO installed hook backs that refusal. `UserPromptSubmit` reads `$oso-code:plan`'s spelling alone, so the wrapper's own instruction is the whole of that boundary, and it says so where an operator and a model both read it.

## Context

The operator's complaint was concrete: when several substantial changes are known up front, the decisions that shape them are largely the same decisions, and `/plan` asks for them once per change. Five changes meant five intent approvals, five sets of decision rounds mostly re-answering the last set, and five plan approvals — with the operator present for every one of them, since each of Mode 1's gates is written for somebody standing at it.

The alternative of loosening Mode 1 — letting one plan carry several changes — was rejected: the ledger, the slices and the verify bar of a plan are one change's, the close is one change's, and a plan that carried five would have five bases, five sweeps and one index row that could not say which of them was executing. What the operator wanted was not a wider plan but a queue of them with the deciding pulled forward, which is a different flow and gets its own mode.

## Consequences

- Mode 1's gates gain a second reader. Four of them had no reachable exit without an operator, which is ADR-0137, and the two texts that hand a decision to the operator keep their instruction word for word while naming the one condition that answers instead. Nothing in Mode 1 changed for a change the operator is standing at.
- Behavioural acceptance of this mode is the operator's FIRST REAL ROADMAP RUN, and nothing in this repository can stand in for it. The bar this change closes at is the harness's own — the full hook suite with the linter transitive, both plugin manifests validated, the rendered hook manifests and their published hashes — and every one of those judges text and shell, never a queue of real changes carried unattended to its close. The change ships with that acceptance explicitly PENDING rather than implied by a green suite.
- Codex operators read a mode whose headline promise does not hold for them, which is why the loss row is a release requirement and not documentation: an operator who reads "decide once and walk away" and then sits through four approvals has been misled by the harness, not by the host.
- `codex/.codex-plugin/plugin.json`'s `interface.defaultPrompt` keeps its three starter prompts and does not gain a fourth for this mode. The Codex plugin manifest spec caps that array at three prompts of at most 128 characters each, so a fourth entry would be an invalid manifest rather than a fuller one; the fourth mode is carried by the two description fields beside it.
- The mode is invisible to model invocation on both hosts (`disable-model-invocation: true`), so it starts only when the operator asks for it. A model that could start a roadmap could start an unattended chain over a queue nobody approved, which is the one failure mode this whole design is built to make impossible.
