# 0125 — Four installer-integrity defects from an external audit, and the CLI pin becomes a precondition

Date: 2026-08-06
Status: accepted
Reconciled: applied — every file above carries the change this decision records.
Source: an external audit of `740cad3`; each claimed defect was reproduced on a scratch fixture before being fixed (measured: `cp -R` preserves a symlinked role file into the staging area, a plain `cp` onto it writes through, `chmod` follows it too; an unescaped `.` in a `sed` BRE pattern matches an arbitrary substituted character, normalizing a wrong path to the expected hash; the standalone Codex release on the machine this pin was read from runs to ~300 MiB, matching order of magnitude to the whole 300 MiB `INSTALL_BACKUP_BUDGET_KIB` every other snapshot shares (D14, ADR-0124); `codex plugin list --json` against a real marketplace install, read directly)

## Decision

### 1 — A symlinked role file no longer lets `install_agents` write outside `~/.codex`

`preflight_agents` already refused a symlinked `AGENTS_TARGET` itself, but `install_agents`'s role-file loop did not check each entry it wrote. `cp -R "$AGENTS_TARGET/." "$stage/"` preserves an existing symlink inside the target directory rather than dereferencing it; the loop's own `cp "$role" "$stage/$(basename "$role")"` is a plain `cp` (no `-d`/`-P`), which follows an existing destination symlink and writes through to whatever it names, and the following `chmod 600` follows it too. Both were confirmed by reproducing the exact sequence in a scratch fixture: a symlink named `oso-applier.toml` pointing at a sentinel file received the new role's bytes and a `chmod 600`, while the symlink itself was left standing. The fix is one line: `[ -L "$dest" ] && rm -f "$dest"` before the `cp`, so the write and the chmod always land on a fresh regular file the staging area owns, never on a link's target. The final tree is unchanged for every install that never hits this case — a symlink there is not a normal state, only ever an artifact of a prior tool or an adversary.

### 2 — The published-runtime check no longer treats a path's own dots as a wildcard

`verify-codex.sh`'s `installed_trust_status` normalizes an installed `hooks.json` back to its published `__OSO_HOOKS_DIR__` placeholder with `sed` before hashing it, so the hash can be compared against the one hook-hashes.txt already publishes for the placeholder-carrying template. The escaping applied to `RUNTIME_ROOT` before building that `sed` pattern (`\`, `&`, `|`) is the escaping a **replacement** string needs — the same escaping `install-codex.sh` already uses correctly at its own two call sites, where `RUNTIME_ROOT` is the replacement, not the pattern. `installed_trust_status` uses it backwards: `RUNTIME_ROOT` is the **pattern** there, and a BRE pattern's `.` is unescaped and therefore matches any single character. Every real `RUNTIME_ROOT` carries a literal `.` (`$HOME/.local/share/oso-code/runtime`), so a manifest naming a directory that differs from the real one by exactly that one byte (`Xlocal` for `.local`) still normalized to the same placeholder and the same hash — `published runtime bytes: verified` reported for bytes the manifest never actually carried.

The fix is a new `escape_sed_pattern` helper (`\`, `.`, `*`, `[`, `]`, `^`, `$`, and the `|` delimiter) used to build the pattern side, leaving `install-codex.sh`'s own replacement-side escaping untouched — the two are different problems with different correct escape sets, and conflating them was the bug. Verified both directions on the same fixture: a path one metacharacter off the real `RUNTIME_ROOT` is now reported as `bad:` and names `codex/hooks/hooks.json`; the real path still normalizes and verifies exactly as before.

### 3 — The Codex CLI pin is a precondition, not a step inside the transaction

**The choice, and why the other option was rejected.** Moving `npm install --global @openai/codex@<pin>` inside `begin_transaction`/`rollback_transaction` was the other live option, and it is mechanically easy: `backup_target` already snapshots an arbitrary path with `cp -a` and replays it with `restore_backup_manifest`, so backing up wherever `npm root -g` resolves `@openai/codex` to would cost no new machinery. It is rejected on a measured number, not a guess: the standalone Codex release present on the machine this pin was read from runs to **~300 MiB** for the CLI alone — on the same order of magnitude as the **entire** 300 MiB `INSTALL_BACKUP_BUDGET_KIB` every other snapshot in a transaction already shares (D14, ADR-0124, itself sized against a measured 1.9 GiB problem). Backing up the CLI on every run, even the overwhelming majority where it never changes, would either blow that budget on one artifact or force a second, larger budget for a resource none of `begin_transaction`'s other eleven targets resembles: everything else it backs up is a file this project renders under `$HOME`, never a large, independently-versioned binary owned by a package manager.

**The precondition.** `ensure_codex_version` is renamed `preflight_codex_version` and stops calling `npm install` altogether: it now only reads the installed version and fails, naming the exact command the operator must run (`npm install --global @openai/codex@$SUPPORTED_CODEX_VERSION`), if it does not already equal the pin. It moves into `main`'s existing preflight sequence — before `confirm_install`, matching every other `preflight_*` check's own placement — so a machine not already at the pin never reaches `begin_transaction`, never gets a confirmation prompt, and never mutates anything this installer owns. D14 (ADR-0094) pins *which* version is supported; it does not require this script to be the one that installs it, and nothing here changes the pin itself, `@latest` still never appears, and the post-install verifier's own separate version check is untouched.

**Why this satisfies D20.** `rollback_transaction` can only ever restore what `begin_transaction` backed up. A step that mutates something outside that backup — the prior in-place `npm install`, which ran *before* `begin_transaction` even started — is exactly the shape D20 already named in ADR-0110: a step the rollback cannot reach. Making the CLI version a refused precondition instead of a step removes the mutation from this script's own responsibility entirely, so there is nothing left for any later failure's rollback to fail to cover.

### 4 — The installed-plugin check matches every field exactly

`plugin_install_status`'s prior predicate was `"oso-code" in json.dumps(installed)`: a substring test over the whole dumped array. Read directly off a real `codex plugin list --json` against an installed oso-code marketplace, an installed entry carries `pluginId`, `name`, `marketplaceName`, `version`, `installed`, `enabled`, and `source.{source,path}` — none of which the old check inspected individually. Reproduced on three fixtures before fixing: a plugin named `not-oso-code` (contains the substring), a correctly-named plugin sourced from a backup-shaped path (`/tmp/oso-code-backup/codex`, also contains the substring), and a correctly-named but `enabled: false` plugin — all three satisfied the old predicate.

The new check parses the listing and requires, on one entry: `pluginId` equal to `<name>@<name>` read from this checkout's own `codex/.codex-plugin/plugin.json` (never a second hardcoded copy of the name), `marketplaceName` equal to that same name, `version` equal to that manifest's own `version` field (so the check tracks a release bump automatically instead of rotting against a frozen second copy), `installed` and `enabled` both exactly `true`, and `source` exactly `{"source": "local", "path": "<MARKETPLACE_ROOT>/codex"}` — the literal path this installer renders. All three prior false positives now fail; the real installed entry still passes.

## Consequences

- `install-codex.sh` no longer auto-repairs an out-of-pin Codex CLI; an operator on the wrong version must run the named `npm install --global` command themselves before the installer will proceed. This is a deliberate loss of convenience for an honest transaction boundary — see Decision 3.
- `bootstrap/verify-codex.sh`'s `escape_sed_pattern` is used only by `installed_trust_status`; `install-codex.sh`'s own replacement-side escaping at `render_hook_manifest` and `preflight_hooks_manifest` is untouched, since it was already correct for what it escapes.
- CI's pinned `verify-codex.sh` failure count (14) is unchanged — measured directly against the exact fixture `.github/workflows/ci.yml` runs (fresh `HOME`, no `codex` on `PATH`, `OSO_VERIFY_SKIP_SMOKE=1`): both changed checks were already failing in that fixture (nothing installed to verify or list), and neither fix adds or removes a `check` call.
- Tests exercising the old auto-upgrade behavior (`tests/hooks-test.sh`) are rewritten to assert the refusal instead: an old CLI now fails before any prompt, makes exactly one `codex --version` call and no `npm` call, and the refusal names the exact pin command. A new ordering assertion greps `install-codex.sh`'s own source for `preflight_codex_version` preceding `confirm_install` preceding `begin_transaction`, and for zero bare `npm install` invocations, so criterion (c) cannot silently regress.
