# 0113 — The stale-state warning names only this repository's own file

Date: 2026-08-05
Status: accepted
Reconciled: applied — `warn-stale-state.sh` resolves one file (`state_file_for(cwd)`) instead of sweeping `$OSO_STATE_DIR/*.state`, and its message drops the claim that a repository-keyed file arms this session's gates regardless of whose repository it names.
Source: operator complaint, live during this change — a session in `oso-code` was told about a `.state` file that resolved to an unrelated checkout (`loyalty-landing`) two directories over; D18 (forward recovery — a message naming something the operator cannot act on is the shape this rail exists to remove)

## Decision

**The hook reads one file, not the state directory.** Every gate a session actually meets — `block-edits-without-slice.sh`, `block-commit-until-green.sh`, the git `pre-commit` hook — resolves `state_file_for(cwd)` and nothing else (confirmed by reading all three before this change: none of them glob `$OSO_STATE_DIR`). A file belonging to a different repository therefore arms no gate this session will ever meet. `warn-stale-state.sh` previously globbed every `*.state` file on the machine and compared only the `session` key, so any other repository's live or abandoned state was reported here — true of the state directory's contents, false of anything this session's gates read. The fix resolves the same one file the gates resolve, from the same input (the payload's `cwd`, confirmed present on both hosts' `SessionStart` payload — Claude's documented `BaseHookInput` and the pattern already relied on by both `PreToolUse` gates wired for Codex too), and warns only when that file names a session other than this one.

**The false claim is gone because the scope changed, not because the sentence was reworded around it.** The old message said "State is keyed by repository, so the flags in it arm this session's gates too" as a general rule — true of repository keying in the abstract, false of the specific foreign file the message had just named, since a gate keyed by repository reads *this* repository's file, never the one named. The new message keeps the same sentence shape ("its flags arm this session's gates too") but it is no longer a generalization: the file named is now always the one `state_file_for(cwd)` resolves for this session, the exact file every gate here will read. The claim did not get corrected in place; the scope that made it false was removed.

**The remedy is unchanged in form, and now honest.** `"$OSO_STATE_BIN" --session "$session_id" clear` resolves its target from the caller's own `$PWD` (`oso-state`'s `clear` action, unconditionally); it was never able to reach a foreign file no matter what session id it carried. Once the hook only ever names this repository's own file, the remedy — run from this session's own cwd — reaches exactly what the message names.

**No cross-repository signal replaces the sweep.** Three things were weighed and all argued against inventing one: (1) most state files carry no `repo_path` — that key is written only when a wave is armed (`n=<absolute path>`, plan mode's parallel execution) — so a remedy naming another repository's path would be fabricable for some files and not others, an inconsistent guarantee worse than none; (2) `oso-state` has no flag to target a repository other than the one it runs in, so even a known `repo_path` yields no single runnable command, only a `cd <path> && …` the operator must trust points somewhere real and not build themselves; (3) `cleanup-state.sh`'s `prune_abandoned_state` already removes an abandoned repository's file after 7 idle days (ADR-0057), so a foreign file left behind is not a permanent, silently-growing liability — its worst case is bounded and self-healing without an operator ever reading a warning about it. The sweep's only unique value was visibility into a fact the operator could not act on from here; D18 is explicit that naming such a fact is the shape this whole rail exists to remove, not a lesser evil to keep alongside a working remedy.

## Consequences

- A session in one repository is never told about another repository's runtime state, live or abandoned; the only state a `SessionStart` message can now name is this session's own repository's own file.
- The resume case — a crashed or otherwise-abandoned session's flags still armed in THIS repository — is unchanged: the hook still fires, still names the file, and the remedy still clears exactly it.
- `tests/hooks-test.sh`'s `SessionStart` block asserts all four: silence with only a foreign repository's state present, the fire-and-name behavior for this repository's own stale state, that the offered remedy actually clears the named file when run (not just that its text looks runnable), and that the old blanket claim about a repository-keyed file's flags is gone.
- A machine that accumulates crashed sessions across many repositories gets no single-session visibility into that fact any more; `prune_abandoned_state`'s 7-day sweep is what still bounds it, silently, the way it already did for every state file this hook was never able to make actionable in the first place.
