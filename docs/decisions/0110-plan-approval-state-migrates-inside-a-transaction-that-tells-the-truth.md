# 0110 — Plan-approval state migrates inside a transaction that tells the truth

Date: 2026-08-05
Status: accepted
Implemented-in: bootstrap/install-codex.sh, tests/hooks-test.sh, docs/blueprint.md
Reconciled: applied — `install-codex.sh` sources `plugin/hooks/lib.sh` after `verify_published_hooks` confirms its bytes, gains `migrate_plan_approval_state` (called once, inside the transaction, right after the backup) and `rollback_transaction` now checks and reports every restore item instead of printing one unconditional closing line.
Source: ADR-0107 (526a558) split `session` from `plan_approval_session`; D20 records that 0.19.0 must not manufacture ADR-0107's own bug on an installed base that predates the split, and that the transaction's rollback — the one step this release has no other way to revert — must report what it actually did.

## Decision

**The installer migrates a pre-split state file inside the same transaction that installs everything else.** `migrate_plan_approval_state` runs once `begin_transaction` has taken its backup, walking every `*.state` file under `OSO_STATE_DIR` for one shape: `plan_approval=pending` with no `plan_approval_session` key at all — a file only the pre-ADR-0107 writer could have produced, since every writer since backfills that key at capture time. Each matched file is registered with `backup_target` (the same mechanism `begin_transaction`'s twelve fixed targets already use) before it is touched, so a later step's failure rolls the state file back with the marketplace, the hooks manifest, the config and everything else — never leaves it half-converted. Nothing else about the schema changes: a file without `plan_approval=pending`, or one that already carries `plan_approval_session`, is left alone, satisfying the idempotency `oso-state`'s own design already promises.

**Two cases, not one, read from the old `session` value:**

- **It still names a real presenting session** (anything other than the ownership marker `1`) — the value `capture-plan`'s Stop hook wrote before any later model-issued write could overwrite it with the shared marker. That pending is still legitimately approvable by the session that presented it, so it is backfilled: `plan_approval_session=<that value>` is appended to the file, `session` and every other key untouched.
- **It is the ownership marker (`1`)** — a later model-issued write already clobbered the real identity, and nothing else on disk records it. This pending can never be approved (`approve-plan-token.sh` compares against `plan_approval_session`, which does not exist) and can never be cancelled by the session that presented it either, for the same reason. It is the trap ADR-0107 closes, reproduced by a state file the split never touched. **It is cleared, not preserved.** `oso-state` can set a key but never delete one — `cancel-plan` and the SessionEnd sweep (`clear_orphaned_pending_of`) already clear a pending the only way that constraint allows: the whole file, matching `oso-state clear`. The migration does the same. Leaving the marker-owned pending standing would ship a repository permanently armed with no session on disk that can ever disarm it — a state strictly worse than a clean file, since every local tool outside the allowlist stays denied for as long as the leftover file exists, for any session that later works there.

Each migrated file is reported with `info`, one line per file naming the digest and what happened — the operator's visibility into "what moved," the same channel the existing checkout-hook migration already uses.

**The rollback that protects this migration must itself be trustworthy.** `on_exit` calls `rollback_transaction || true`; that conditional context disables `errexit` for the whole function, so before this decision every `rm -rf` and `cp -a` in its restore loop could fail silently and the function still printed "rollback complete" unconditionally. `rollback_transaction` now checks every restore item explicitly — `rm -rf` the stale target, then (for a `present` item) `mkdir -p` and `cp -a` the snapshot back — and counts and names any that fail, without stopping the loop: a partial restore is better than a stopped one, so one item's failure never costs the remaining items their own restore attempt. The closing message is now conditional on the actual count: `rollback complete` only when every item restored, `rollback incomplete: N item(s) failed to restore (…)` naming them and pointing at the still-present snapshot for a manual restore otherwise. `rollback_transaction` returns nonzero on a failed restore for the same reason; `on_exit`'s `|| true` is unchanged and still absorbs it, so the exit code `on_exit` re-raises stays the original failure's, never rollback's own — the honesty is in what gets printed, not in a changed exit contract.

## Consequences

- 0.19.0 installs cleanly onto a machine whose state predates ADR-0107's split: a legitimately pending plan keeps working exactly as it would have if captured under the new scheme, and an unrecoverable one is gone rather than silently denying tools forever.
- The migration is idempotent by construction (`plan_approval_session` presence is the only gate), so a reinstall or a second run of the installer never re-touches a file it, or a normal capture, has already handled.
- A disk-full, permissions, or read-only-mount failure during rollback — the scenario this release is most likely to hit, since it is the one adding a new write path to a directory the installer did not previously touch — now tells the operator the truth: how many items failed, which ones, and that the pre-install snapshot is still on disk to restore by hand. Before this decision the same failure printed "rollback complete" and left the operator with no reason to doubt it.
- No new snapshot is created per run beyond the one `begin_transaction` already takes; the migration's backups are additional entries in that same manifest, not a second transaction. Snapshot retention remains out of scope (slice B14).
