# Plan mode — OpenCode

## The delivery contract

The adapter makes no claim about whether OpenCode preserves operator-facing text before a same-turn tool call, and the harness depends on no such behavior. It applies the conservative host-independent policy: operator-facing content ENDS the turn as plain text, with any tool call in a LATER turn. An extra turn is the cheap side of that boundary; content the operator never sees is the expensive one.

## Question rounds

The tool is `question`, and it is available inside this flow only when the operator is watching the TUI: headless sessions deny `question` by default. Its schema accepts several questions in one call — the operator navigates between them before submitting all answers — so a decision round holds 3 per round, the way the neutral body spells. A fourth question starts the next round; it never rides an invalid call and never gets dropped. In an unattended run the permission rule for `question` is part of the kill switch while the approval is pending. The tool is yours alone: every agent under `opencode/agents/` is `mode: subagent` and denies `question` outright (D14, F46), so a forked judge or applier can never ask back — it returns `blocked` and the question becomes yours to put.

## The approval gate

Phases 1–5 run on `build`, the primary agent `/oso-plan` routes to and the one every other mode on this host runs on. A read-only planning agent is not open to this flow: the command's frontmatter names one agent and this flow hands its conversation to no other, so the agent that plans phases 1–5 is the agent §6 runs on — and §6 must write state, cut worktrees and commit. What keeps phases 1–5 read-only is the FLOW's own rule, that nothing before §6 writes code, with the `edits` gate on `tool.execute.before` behind it — the same floor `../../oso-roadmap/references/opencode.md` states for a child's planning phases. The gate is the `oso_plan_approve` tool this host's plugin registers, and it binds to the host's PERMISSION GRANT rather than to a turn or a text (D8). The installed config declares `permission.oso_plan_approve: ask`; the tool asks the host for that permission from inside its own execution, so the host raises its authorization prompt and blocks the call until the operator answers. Both halves are load-bearing and were measured on the pinned binary: with the config entry removed the host's base `"*": "allow"` rule lets the call through with no prompt at all, and a plugin tool that never asks is not gated by the config entry alone.

The plugin runs `capture-plan` BEFORE raising the prompt and `approve-plan` — ownership and content-parity checked — only after the grant returns. A refusal arrives as a rejection thrown into the tool call, so the tool reports an error and NOTHING is recorded; a promotion that cannot be written also throws rather than reporting success. The request carries an EMPTY `always` list, which is what makes every approval prompt: an operator answering "always" persists no rule, so no earlier grant ever carries over to a later plan.

Deliver the complete §5 document as turn-ending plain text, then call `oso_plan_approve` in a LATER turn carrying those exact bytes; the operator's answer to the host's prompt is the whole of the approval, and the digest it is bound to is the digest of the bytes you passed. Until that grant lands, do not save Engram plan state, arm a slice or call an implementation tool. The session-scoped permission rules are the kill switch while the approval is pending (D3).

This is the ONE authorization prompt the HARNESS raises of its own accord during a run: every agent's permission block is otherwise tight enough that the host asks the operator nothing, and `oso_plan_approve` is the named exception (D14). OpenCode keeps one of its own beside it, and an unqualified "no prompts" would overclaim past the measurement: the base ruleset carries `doom_loop: "ask"`, no agent block overrides it, and it fires when the last N parts repeat one tool with identical input. That prompt is the host's, the seven blocks and their precedence are recorded with it in `docs/parity-opencode.md`, and nothing in this flow can suppress either. `oso_plan_cancel` is the only other `ask` the installed config carries, and it never surprises anyone — it prompts only in the turn the operator has already asked to abandon the plan in. Under plain AUTO that gate is crossed with the operator present, before the unattended marker arms; under a roadmap a child never crosses it at all (D26), and `../../oso-roadmap/references/opencode.md` states what stands in its place — the one approval that mode's §3 took, and the plain-text delivery §5's document rides instead of the `plan` argument above. Where this change is running as a child of that chain, read it there before phase 1 and present no gate the roadmap already passed.

## The operational plan, its amendments and the way out

`capture-plan` never runs here — the plugin writes the two artifacts itself — so `oso_plan_approve` publishes the plan's runtime state in the same execution the grant returns in, and publishes it only as APPROVED. Beside `mode=plan` it writes the six keys `amend-plan` reads back: `plan_approval=approved`, `plan_approval_digest`, `plan_approval_session`, `plan_snapshot_file` (the immutable `approved-<approval digest>.md`), `plan_current_file` (`current.md`) and `plan_revision=0`, all under `~/.local/state/oso-code/plans/<repository digest>/`. The owner in `plan_approval_session` is `OSO_AGENT` — the same identity the artifact's own ownership marker carries and the same one every other state call on this host spells — so one `--session` covers the whole lane and no second identity lives in the state file. A PENDING approval is deliberately never armed here, and that is what keeps the catch-all's pending deny inert: that deny closes every local tool for the session it names, and both of Codex's ways back out of it ride `UserPromptSubmit`, a hook this host does not have — so a pending window would brick the session instead of failing closed (D11). Nothing is lost with it, because on this host there is no interval between presentation and grant for a pending state to describe: the grant IS the approval.

The immutable `approved-<approval digest>.md` answers what the operator approved; never edit or replace it. `current.md` answers what remains to execute and may change only through a recorded operational amendment. Engram remains the cross-session semantic index, so every accepted amendment updates BOTH `current.md` and the existing `oso/{change}/plan` observation; neither store silently outranks the other. An amendment is issued through the state command exactly as §5's and §6's own state writes are — same spelling, same owner, same read-back — and never as a hand edit of `current.md`, which records no event and moves no revision.

An explicit operator request may add a hot slice without a new approval only when every condition holds: it stays inside the frozen intent and scope; preserves every ledger decision; introduces no new contract, migration, auth/security/rollback surface, dependency policy, base ref or execution-mode decision; carries Goal, Files, Verify and Depends-on; and does not rewrite an active or completed slice. The operator's request is the amendment authorization. Append the slice after the active sequential slice or after the current parallel wave — never inject work into a unit already in flight — then pipe the complete slice block to `"${OSO_STATE_BIN:-oso-state}" --session "${OSO_AGENT}" amend-plan <slice-id>`, read `oso-state show` back, and `mem_update` the plan topic with the same pending slice and position. The state command appends a dated in-scope amendment to `current.md`, increments `plan_revision`, records the event and returns `verify_green=false`; it never edits the immutable snapshot.

If any condition fails, the request is material. Recommend saving it as a new `roadmap` row in Engram — this host runs that queue, and `../../oso-roadmap/references/opencode.md` is the mode that carries it — and finish the active change unchanged. If the operator requires it for the active outcome, re-present and pass a fresh approval instead; approval has no meaning if architecture or scope can expand later through an ordinary execution prompt.

**A harness-discovered correction to a not-started slice may also amend `current.md` through one operator confirmation, never a full re-approval, when every condition holds:** the target slice has NOT STARTED — never armed as `active_slice` and carrying no `[x]` in the Engram plan; a slice already active or completed takes the material-change route above instead, unchanged. The correction CITES the evidence that disproves the slice's premise — the file and line of the installed artifact its premise contradicts; an uncited correction is the harness rewriting an approved slice on its own assertion, so it is never eligible here. Present the citation and the corrected fact to the operator, who CONFIRMS in one line — not a re-read of the plan; that confirmation, never the harness's own finding, is what authorizes the amendment, exactly as the operator's own request authorizes a hot slice above. On confirmation, pipe the citation, what changes, and the corrected slice fields to `"${OSO_STATE_BIN:-oso-state}" --session "${OSO_AGENT}" amend-plan <slice-id>`, read `oso-state show` back, and `mem_update` the plan topic and the ledger with the same correction — the identical mechanics the hot-slice paragraph above already relies on, so the amendment and its event RECORD the same way. Any single condition missing routes to the material-change rule instead, never this lane.

A material change to the document invalidates prior approval under §5: present the complete repaso-first plan again as turn-ending plain text and call `oso_plan_approve` again in a later turn. That second call binds a FRESH digest and raises the host's authorization prompt again, and the operator's answer to it is the whole of the re-approval. Nothing inside this lane can stand in for it: `amend-plan` moves `plan_revision` and `verify_green` and touches no approval key, and the `approve-plan` verb can never fire on this host at all — it requires the PENDING state nothing here ever arms — so the promotion happens only inside `oso_plan_approve`, behind that prompt. Never treat an earlier grant as authority for changed scope or frozen decisions.

Feedback BEFORE the grant is not an amendment here and never reaches `amend-plan`: there is no persisted pending document to amend, so pre-approval feedback is ordinary conversation inside this mode, which re-presents the corrected plan and crosses the grant again on a new digest — the material-change mechanism doing that work. `docs/parity-opencode.md` records that as a host-justified divergence from the Codex pending-feedback lane.

To ABANDON the plan instead, the operator asks for `oso_plan_cancel` — the grant-bound spelling of the Codex `CANCEL OSO PLAN` token, whose own mechanism is a magic prompt on a hook this host does not have. It raises the same kind of authorization prompt the approval does, refuses before prompting when this repository holds no approved plan of its own, and on the grant writes `mode=plan active_slice=none verify_green=false` beside `plan_approval=cancelled` — closing the edit and commit gates and leaving nothing for the amendment lane to amend. It runs no `oso-state clear` and touches no other key, so an unattended run's `auto` marker, its `auto_change` and the approved document itself all survive the abandonment. Never approve merely to gain a tool call, and never call the cancel tool to unstick a denied one.

## Shared-file paths

Wherever the neutral body names a file as `_shared/<file>.md`, it is spelled `../_shared/<file>.md` here, resolved against the directory holding the `SKILL.md` you were routed through — the resolution rule OpenCode states for every relative path a skill writes (the `skill` tool returns content with "Relative paths in this skill are relative to this base directory"). Expand it to an absolute path before putting it in a payload another context reads.

## The state command

`OSO_STATE_BIN` reaches every tool subprocess on this host through the installed plugin's `shell.env` hook — which fires per shell invocation and whose `output.env` values ARE present in the tool process environment. So `oso-state` is spelled `"${OSO_STATE_BIN:-oso-state}"` here.

What the state is keyed by is settled and is host-neutral: the state file is the REPOSITORY's, resolved from the directory the command runs in.

This host publishes the ROOT session id through `shell.env` for tool subprocesses (D13); that value is what `OSO_AGENT` carries, and it is never exported into the server process itself. Spell every state call as `"${OSO_STATE_BIN:-oso-state}" --session "${OSO_AGENT}" <verb> …`. The lineage map root→child is the installed plugin's, and the git hook and the session-scoped permission rules read the same marker.

## The runtime gates, and the two layers of the commit rail

The installed plugin's `tool.execute.before` hook is the gate rail: a throw inside it blocks the tool and surfaces the reason to the model (F7). The TS shim spawns the existing bash gate scripts unchanged and translates all three exits (D1): deny JSON → throw; empty stdout → allow; exit 2 + stderr → block. The commit gate and the edits-without-slice gate ride `tool.execute.before`; the unknown-tool catch-all deny closes every tool outside the allowlist while a slice is armed (D26). Until the installer (S13) has materialized the plugin and the operator has confirmed the config, report the gates as installed but not enforcing and never describe them as active.

## What the unattended marker arms on this host

Three rails read the `auto` marker the AUTO disposition writes, and they are what "unattended" costs and buys here:

- **The continuation rail** — the installed plugin's own code on the `session.idle` bus event (`opencode/plugin/oso/continuation-rail.ts`, its reading in `opencode/plugin/oso/unattended-run.ts`). This host has no refusable stop: throwing from `event` does not hold a turn back, it wedges shutdown. So the rail POSTS a turn rather than refusing one — `client.session.prompt` back into the same session, which lands as a real user turn — and `plugin/hooks/auto-continue.sh`, whose only output channel is a `Stop` decision, never runs here at all. Two bounds hold it, and they are the same two the Claude net states: a TURN bound of 3 posted turns that moved the run journal nowhere, and a WALL-CLOCK bound of 45 minutes on a delegation mark. `session.idle` fires once per `opencode run` turn and twice per interactive one; one driver per session covers both cadences, because the second idle of a turn finds the first still posting and is dropped. A session the bus announced with a `parentID` is a wave child and is never continued — the state file's owner is repository-scoped on this host and cannot tell a child from the run's own session.
- **The re-anchor rail** — `reanchor-after-compact.sh`, run from the `session.compacted` bus event. A compaction takes the window and not the position: the gate hands the fresh context the three places the position actually lives — the `oso/index` row's `NEXT:` line, `oso-state show`, and the run journal — and its text rides the system prompts that session assembles next.
- **The production boundary** — `block-prod-deploy.sh` on `tool.execute.before`, armed only while the marker is running: a production deploy, and a push off the run's own `oso-run/*` branch, are denied to a run nobody is watching. A denial is one tool call refused and nothing more; the run continues past it. Taking the run back (`auto=done`) is what disarms it.

The marker is the flow's to write, never a rail's: `"${OSO_STATE_BIN:-oso-state}" --session "${OSO_AGENT}" set auto=running auto_change=<change-slug>`, then `auto=parked` and `auto=done`, exactly where `../_shared/unattended.md` puts each flip. No rail writes any of the three, and nothing here arms a run past an approval — under plain AUTO phases 1–5 run with the operator and the grant above is crossed before the marker exists (D26).

**The terminal steps are the neutral body's own** (§7 step 8) and this host changes only what carries them: the FINISH is `git -C <main checkout> push -u origin oso-run/<change>` followed by the PR through `gh pr create` in a bash call, and the run branch is the only one the production boundary lets that push name. The PARK and the FINAL REPORT are deliveries, so each ends the turn as plain text under the delivery contract at the top of this file, with the disarm (`auto=done`) sequenced as the tool call BEFORE the report's text. A milestone ends the turn here too — this host gets no carve-out from that contract — and the continuation rail is what carries the run across each of those turn ends. It costs the turn bound nothing, because every milestone is also appended with `oso-state journal`: the journal grows, and journal growth is exactly what resets the count of posted turns that moved it nowhere.

## The worktree root

`<worktree root>` is the host's worktree space under `$HOME/.local/share/opencode/worktree/<projectID>/` — the path this host's workspace API creates worktrees at (plan §3 trap 5). Cutting the trees is YOURS and the command is the neutral body's own: `git -C <main checkout> worktree add -b oso/<change>/<slice> <worktree root>/<slice> <wave start>`, run against that space before any child is launched. The installed plugin creates no worktree — its workspace adapter registers under the type `oso-code` for discovery only and its `configure` throws by name pointing at `oso_wave` (S9), so the host's own workspace dialog cuts nothing here — and `oso_wave` runs no git either: it pins each child session to a worktree that already exists by carrying `directory`, and refuses a path that is not a git worktree of this project. Every slice still receives its exact absolute worktree path and its ref coordinate (SLICE START or WAVE START).

## Naming and invoking the harness's own skills

Installed plugin skills carry NO namespace on this host: every skill auto-registers as a slash command under its own `name`, and the installed `opencode.json` carries `permission.skill` deny rules for the three operator-only modes, hiding them from the model while the slash command stays (D11; empirically verified on the pinned host). Operator-invoked modes use that command spelling; an orchestrator opens and reads auxiliary `SKILL.md` files in the installed tree.

| the QUICK mode | `/oso-quick` | the operator invokes `/oso-quick` — a mode is never model-invoked |
| the DEBUG mode | `/oso-debug` | the operator invokes `/oso-debug` — a mode is never model-invoked |

Forked judges and operational agents are the exception to inline reading: launch them by their `opencode/agents/` contracts, passing SKILL PATH and ARGUMENTS in the payload (D10), under the wait rule below.

## Making a launch wait

No launch on this host outlives the turn that made it, so nothing here waits for a report that arrives in a later one. The `task` tool is SYNCHRONOUS — the call blocks until the child turn completes and the child's own final message comes back in-band (plan §3 trap 5, D5) — and there is no wait operation and no handoff receipt rail beside it (D5), so that returned message is the whole of the handoff. **Nothing may act on a report it has not read**, and here reading it is what the call returns: a launch that errors, times out or returns an empty verdict BLOCKS the flow and never falls through to the next step, and a second launch over the same tree is two writers in one slice rather than a way to collect a verdict the first one already gave.

`auto_wait` is therefore never armed here. That marker exists for a host whose report arrives in a later turn, and this host has no turn to bridge; the continuation rail reads the key only to notice one left standing, and treats a mark older than the 45-minute wall-clock bound above with no milestone journaled since as LOST — its order is to disarm it (`auto_wait=none`) and continue, never to keep waiting on a delegation this host cannot have in flight.
