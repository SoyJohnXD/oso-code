# The gates, once, for every host the harness runs on. tools/render-hooks-json.sh
# turns this table into each host's manifest: hooks.json for Claude and Codex,
# and a TypeScript route table (opencode/hooks/routes.ts) for opencode, whose
# gates are a TS shim rather than subprocess hooks. tests/plugin-lint.sh's
# check_hook_renders_and_published_hashes_match fails when a committed manifest is
# not what it renders. Nothing here is written twice: the matcher a host spells
# for a gate is a cell in this file and nowhere else.
#
# Four record kinds, each labelled by its first field. `host`, `gate` and `tool`
# each end in ONE CELL PER HOST in the order the `host` rows appear; `recovery`
# carries prose and is read by nobody but the parser's presence check and you:
#
#   host <name> <manifest, relative to the repo root> <command root>
#   gate <id> <event> <script under the hooks directory> <wired|none per host>
#        <mechanism per host>
#   recovery <gate id> <the operator's legitimate next step, in prose>
#   tool <gate id> <the name that host spells the tool with, or none, per host>
#        <read|write|role> <yes|no>
#
# A gate row answers each host TWICE, in the same host order: first whether that
# host runs the gate SCRIPT, then by what mechanism. `subprocess` is the answer
# for every Claude and Codex gate that runs — the host spawns the script on the
# event column's event. opencode has no subprocess hooks, so its answer is the
# name of the hook the TS shim routes the script from. `native` is the third
# answer neither cell can give alone: the harness delivers that gate's BEHAVIOUR
# from its own plugin code with no script running at all, which is why
# persist-state-bin.sh, publish-subagent-handoff.sh and auto-continue.sh read
# `none` on opencode and are still delivered there. A mechanism that is not the
# one measured for its host is refused before any render, the same way an unknown
# script or event is: docs/parity-opencode.md carries the per-gate evidence
# behind each of them.
#
# A tool row's last two cells are the capability model, independent of how many
# hosts precede them: whether the name READS or WRITES — the class that decides
# whether a tool could ever belong behind the `edits` gate at all, since only a
# tool that can mutate repository files earns that gate rather than the
# `unknown` catch-all alone — and whether the name is MANDATED by a protocol
# this harness itself installs and instructs the model to follow, which is what
# made mem_judge's absence a deadlock rather than an inconvenience (5905a27). A
# `handoff` row names a subagent role rather than an invocable tool, so `role`
# answers its class instead of read or write; its mandated cell is still real —
# the harness's own delegation protocol requires exactly these eight role
# identifiers. Nothing here is a second copy of the renderer's own answer:
# render() below never reads past each row's per-host cells, so these two never
# change a byte of what renders (the same tests/plugin-lint.sh rule asserts the
# committed manifests are still exactly that render).
#
# `none` is an answer, not an omission — the host has no counterpart. A row that
# leaves a host unanswered is refused. Runtime default-deny is separate and real:
# the `unknown` gate — wired on Codex and on opencode, and on Claude not at all —
# renders a final `.*` matcher on both, and its tool rows are
# the exact allowlist passed to block-unknown-tool.sh. Specific Bash/apply_patch
# gates still make their own state verdict; the catch-all only rejects a tool name
# absent here, and only after an oso-code state exists for the repository.
#
# The command root is quoted so a path with spaces survives the shell each host
# runs the command through. Claude Code interpolates ${CLAUDE_PLUGIN_ROOT} itself;
# Codex has no such variable and its hooks are user-level rather than bundled, so
# the installer that places them substitutes __OSO_HOOKS_DIR__ for the absolute
# directory it wrote them to. The renderer also prefixes every
# Codex command with `OSO_AGENT=1`: Codex 0.146 does not pass its tool-command
# shell_environment_policy into the separate user-hook command runner. opencode
# publishes the same identity marker through its own shell.env hook (the parity
# ledger's D13), so no command prefix is needed there.
#
# opencode carries no substituted root at all: routes.ts is TypeScript the
# plugin imports rather than a JSON manifest a host reads, so the module
# always knows its own location and resolves the installed gate tree — a
# sibling `hooks/` directory beside the route table — from import.meta.url.
# Baking an absolute path into an installed file the way Codex's sed
# substitution does would leave a moved HOME silently pointing the gates at
# nothing. The opencode host row's command-root cell is therefore
# documentation only, unread by the renderer.

host  claude  plugin/hooks/hooks.json  "${CLAUDE_PLUGIN_ROOT}"/hooks
host  codex   codex/hooks/hooks.json   "__OSO_HOOKS_DIR__"
host  opencode  opencode/hooks/routes.ts  <module-relative>

# Row order is render order, and on Codex render order is TRUST order: `[hooks.state]`
# keys each trusted hash by position (`<hooks.json>:<event>:<group>:<handler>`), so
# inserting or reordering a row shifts the later groups of that event.
#
# persist-state-bin.sh is Claude-only because its whole mechanism is CLAUDE_ENV_FILE,
# which no other host writes; Codex user hooks get no shell_environment_policy at all,
# so a Codex-wired handler resolves oso-state from the runtime sibling of its own
# hooks directory instead. Wiring it there would cost a trusted position and do nothing.
#
# warn-stale-version.sh is Claude-only for the same reason read the other way: it
# compares an install against the marketplace that served it, and Codex has no
# marketplace — bootstrap/install-codex.sh copies a clone's files to a runtime
# directory, which the `claude plugin` commands its message names cannot reach. A
# Codex-wired handler would either never speak or tell an operator to update an
# install that came from somewhere else.
#
# A PreToolUse gate declares its own way out or it does not land here: a
# `recovery` row below naming the operator's legitimate next step, or explicitly
# stating there is none — never a cause the operator has to translate into an
# action themselves, and never the state write that would disarm the gate it
# belongs to. tools/render-hooks-json.sh's own parser enforces this the same way
# it already enforces a matcher or a script's existence: closed, before any
# render, check or classify mode runs. Stop and UserPromptSubmit gates block
# through a different channel (`stop_block`, `control_block`) this rule does not
# reach yet.

gate  commit    PreToolUse    block-commit-until-green.sh   wired  wired  wired  subprocess  subprocess  tool.execute.before
gate  edits     PreToolUse    block-edits-without-slice.sh  wired  wired  wired  subprocess  subprocess  tool.execute.before
gate  unknown   PreToolUse    block-unknown-tool.sh          none   wired  wired  none  subprocess  tool.execute.before
gate  handoff   SubagentStop  publish-subagent-handoff.sh    none   wired  none  none  subprocess  native
gate  planstop  Stop          capture-plan-approval.sh       none   wired  none  none  subprocess  none
gate  autocontinue Stop       auto-continue.sh              wired  none  none  subprocess  none  native
gate  planprompt UserPromptSubmit approve-plan-token.sh       none   wired  none  none  subprocess  none
gate  statebin  SessionStart  persist-state-bin.sh          wired  none  none  subprocess  none  native
gate  stale     SessionStart  warn-stale-state.sh           wired  wired  wired  subprocess  subprocess  experimental.chat.system.transform
gate  version   SessionStart  warn-stale-version.sh         wired  none  none  subprocess  none  none
gate  teardown  SessionEnd    cleanup-state.sh              wired  wired  wired  subprocess  subprocess  dispose
gate  proddeploy PreToolUse   block-prod-deploy.sh          wired  wired  wired  subprocess  subprocess  tool.execute.before
gate  reanchor  SessionStart  reanchor-after-compact.sh     wired  none  wired  subprocess  none  event

recovery  commit      the deny reads the session's own `mode` and names that mode's own path to green — plan's apply → verify loop, or quick/debug's close step — never a menu of every mode's step, and never the state write that would flip the flag itself.
recovery  edits       the deny names the exact `oso-state` invocation that arms the slice this gate is waiting for — the one thing only this gate knows.
recovery  unknown     this gate denies for two distinct causes and gives each its own way out — a pending plan names Codex's native approval controls; an unlisted tool names the exact allowlist this release actually admits.
recovery  proddeploy  take the run back (`oso-state --session <id> set auto=done`) and run the command from your own terminal — this gate arms only while THIS session's unattended run is still in flight.
